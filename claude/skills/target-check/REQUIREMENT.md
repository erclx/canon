# Target check requirement

## Gap

Without this skill, a session landing in a target project decides for itself what to look at. Nothing tells a dispatched worker what the target holds against what the toolkit ships, so two sessions rarely read the same domain.

Silence is the second half. A verb the target's binary lacks, or an absent report key, looks no different from a clean answer, so an unexamined domain reaches the reader as one that passed.

## Must

- Report one section per domain, read through the verb that already owns that comparison, so a reader can tell which surface a finding came from
- Take the installed domains from the catalog the report returns rather than from a list in the body
- Report a refusal, an absent key, and a missing subcommand as unread with the cause, so an unexamined domain never reads as a passing one
- Report the Claude harness as unchecked on every run while no verb answers for it, as a row rather than an omission, and report the toolkit version first
- Run every read non-interactively, since the caller is a dispatched worker with nobody present to answer a prompt

## Must not

- Repair a finding, write a file in the target, or open a pull request, since a check that repaired as it read leaves the reader unable to tell a finding from a fix
- Emit a verdict across the domains, since a roll-up misstates the domains no verb answers for
- Answer the harness domain by file inspection
- Hardcode a stack, rule, or domain name
- Run at the toolkit's own root, which holds the source rather than an install

## Out of scope

- Document health, which `document-health` owns
- Repairing anything a section names, which the command or skill behind that section owns
- A target's own routes, which `canon inventory` owns
- First-time scaffold, which `target-setup` owns
