# Commands

Every `canon` verb is registered in commander and either handled in TypeScript or dispatched into a `manage-*.sh` script. This file holds what decides which of the two a verb gets, what a migrated verb owes, and the rules a command follows once it is writing files or asking questions.

## Registration

- A migrated command defines its real option surface in commander rather than forwarding argv. `indexes` is the first, so a mistyped subcommand now fails with a suggestion instead of reaching a shell script. Every command still on bash carries `allowUnknownOption()` and parses nothing.
- Commands still on bash stay thin. A command file parses arguments and execs, so behavior changes land in the bash script rather than in two places.
- A flag that carries a default is still distinguishable from one the operator passed. `getOptionValueSource` reports `default` rather than `cli`, which is what lets `canon init` default `--stack` to `base` and keep prompting on a bare run. Read provenance rather than the value whenever a default and an explicit pass have to behave differently, since a value test collapses the two.
- A default belongs on the flag rather than in a branch behind an absent one. The default then shows up in `--help` where a caller can see it, and the resolver stays a single function both the preview and the step list call, so the two cannot disagree about what will install.
- The root program sets `helpOption(false)` for its own hand-rolled help, and subcommands inherit it. A migrated command re-enables help explicitly at each level or `--help` returns an unknown-option error.
- `sandbox.ts` is the exception that carries interactive select prompts before the exec, because the scenario picker needs the TS prompt surface. It also holds the sandbox reads that are not provisioning, with the report logic in `src/sandbox/` so the command file keeps only the framing. Each read is reasoned about in `.claude/context/sandbox/index.md`.
- A `check` subcommand coexists with a pass-through parent by registering after it. `sandbox` keeps `allowUnknownOption` and `passThroughOptions` so `canon sandbox git:commit` still reaches `manage-sandbox.sh`, and commander resolves the named subcommand first. Adding a second such subcommand needs the same ordering.

## Migrating a domain off bash

- A domain migrates one verb at a time. `tooling`, `gov`, and `snippets` register their migrated verbs natively and name each remaining verb as an explicit pass-through, which is what let each dispatcher be deleted before every verb had moved. Naming them, rather than falling back to `allowUnknownOption()` on the whole domain, keeps `--help` honest for the verbs that did move.
- The pass-through registration lives in `src/commands/pass-through.ts` and takes the domain name, since the loop is identical for every domain and only the banner and script path vary. Gov, snippets, and standards all call it. A verb whose script sits somewhere other than `scripts/<domain>/<verb>.sh` registers by hand instead.
- Whichever layer runs first opens the timeline frame, or the bash verb emits a closing `└` with nothing above it. Each pass-through calls `intro` before it execs for exactly this reason, which is the obligation a deleted dispatcher hands upward.
- A pass-through verb sets `helpOption(false)`. Commander resolves `--help` before the action runs, so leaving the built-in option on prints a one-line stub and hides the flag surface the bash script documents. Disabling it lets the flag reach the script, which owns that surface until the verb migrates.
- A step list takes its child-process factory as an argument. `src/init/steps.ts` does, so a test reads the list for its labels and argv without spawning anything.
- Tests run under `bun --bun vitest` rather than plain vitest. Migrated code uses `Bun.YAML`, `Bun.Glob`, and `Bun.$`, which do not exist in the Node runtime vitest defaults to.
- Bash that still needs a migrated capability shells into the CLI by path (`bun "$PROJECT_ROOT/src/cli.ts" ...`) rather than via the global `canon`, so a linked worktree exercises its own code.

## Shared helpers and what earns a command

- A helper lifts to the `src/` root once a second domain needs it. `stripFrontmatter` moved out of `src/gov/payload.ts` into `src/frontmatter.ts` when `docs` arrived, rather than having `docs` import from `gov` and carry a dependency it has no reason to. `copyPreservingMode`, `resolveTarget`, and `cliRun` were lifted the same way.
- `listIgnored` lifted from `src/indexes/walk.ts` to `src/git-ignore.ts` when the comment scan became its second caller, following the same rule.
- A lift lands in a named folder rather than a root file when what moves is a subject rather than a function. `INSTALL_BROWSER`, `isBrowserMissing`, and `isEngineMissing` came out of `src/demo/` into `src/browser/engine.ts` when `canon inventory` became the second command driving a browser, because the three answer one question together, which is what a command needs to know before it can report a failure honestly. A root file per predicate would have spread that question across three.
- Behavior shared across domains lands in `src/sync/` rather than in the first domain that needs it. Gov is the first consumer of the sync engine, and burying it under `src/gov/` would force a move as soon as snippets arrives.
- A domain earns a command when the operation is mechanical, not when the domain is important. Tasks gained `archive`, then `pull-request` and `outcome`, all three of which take a decision a skill already made and apply it to a file.
- Creating a task proposes a phase label from the board and writes prose from a conversation, which is judgment, so it stays in `task-board` and no `create` verb exists to tempt a caller
- A structured edit to shared scratch is the second thing that earns a verb, and worktree isolation is why. `Edit` and `Write` refuse a main-root path from a linked worktree, a shell stream editor is banned for an in-place edit, and a verb resolving the root in-process is what is left.
- `pull-request` and `outcome` are the two the board takes. Creating a whole file earns nothing, since a heredoc through `Bash` writes it safely, which is why no verb exists for a plan or a review report.
- Answering a question no skill can answer alone is the third thing that earns a verb. `sessions list` reads a registry outside the project to say which session holds which branch, where a runbook could only describe the lookup and every session would re-derive it. The test still holds, since the work is a mechanical read rather than a judgment, and the reasoning sits in `.claude/context/cli/overview.md`.
- `sessions list --self` narrows that same read to the caller's own row, which is what a dispatcher reads to learn the `sessionId` it carries into a launch. The join runs on `CLAUDE_CODE_SESSION_ID`, then `CLAUDE_PID`, then the pid the `CLAUDE_CODE_MESSAGING_SOCKET` basename spells, and never on `CLAUDE_CODE_HOST_SESSION_ID`, which holds a `local_`-prefixed value from the harness namespace matching no row. The first two rungs postdate the 2026-08-30 reading that found no roster identifier in the environment at all, so the socket parse is the last rung rather than the only one. Refusals name which half failed, `no-self-identity` where the environment states none of the three and `no-self-row` where it states one and no live row carries it, on the same ground as `no-registry` rather than returning an empty roster.
- Replacing a reading a person was taking by hand is the fourth. `canon records size` reports each record folder's file count, bytes, two mtime windows at 7 and 30 days, and the dates of its least and most recently written file, and it gates on none of them, since a record folder has no correct size and the number is one to notice rather than a threshold. What earned it is that the memory pen went from 44 entries to 236 between two readings taken by hand two weeks apart.
- That growth half rests on `mtime`, which is a proxy that overstates and never understates. A machine restored by `canon records pull` reads its whole tree as new, because a hard reset re-dates every file it writes and nothing on the filesystem separates a restore from a write. The set read is `BACKED_FOLDERS` plus the scratch folder, since deletable without loss is not the same as empty, while `.records.git` is the backup history and `worktrees/` holds checkouts with their own removal verb.
- `canon claude skills list` reads `claude/skills/` alone. Internal skills under `.claude/skills/` are excluded, since a count spanning both reports work that never installs into a target. Each entry carries a `requirement` boolean for the sibling `REQUIREMENT.md`.
- It reports presence and never a reason, and since coverage is universal a `false` is a gap to close rather than a recorded exemption. `canon claude skills audit` sits beside it and gates that rule across both corpora, so the boolean reads the shipped catalog while the audit answers whether a working tree conforms.
- `canon claude skills drift <ref>` is the one verb under `skills` reading history rather than a tree, naming which shipped bodies were rewritten between that ref and `HEAD`. A session holds a skill body from the moment it loads one and re-invoking it does not re-read the file, so nothing else compares the two. The ref is required because `HEAD` is the only default available and would answer every run with nothing moved. Nothing records the commit a session started from, so a caller recovers it from elapsed run time through `git log -1 --format=%H --before='<duration> ago'` and rounds up, which is safe because the report over-reports in that direction rather than going quiet.
- A second route to a stale body needs no age. A session editing a body and then invoking that skill later in one chain replays what it loaded before the edit, which is the ordinary ship shape here since a branch touching `docs-fold`, `git-stage`, or `git-pr` runs those skills at the end. Sixteen shipped bodies moved in `34ce48e6` and six of them ran afterwards from the pre-edit text.
- The verb does not reach that route, since reading history is what closes it off and the edit is still uncommitted while the replay happens
- Which shape the staleness takes decides whether anyone notices. A held body naming a file the branch deleted fails loudly by having nothing to read. One naming a file that still exists while saying something different resolves and reads current, so the session applies the stale rule and reports success, which cost three review passes posted under the heading rule `#1012` retired.
- The report fires only when a caller runs it, and reading it is not acting on it. One session ran the verb at session start, read a moved review body in the result, and applied the stale rule for the rest of the day.
- `canon claude skills reach` is the fourth verb under `skills` and reads the shipped bodies for a path their reader cannot open, keying on ownership rather than on existence. It reports and never gates, since a body naming a toolkit path is sometimes a toolkit-scoped instruction, and `.claude/context/cli/audits.md` carries the ownership key, the qualifier, and why both landed where they did.
- Reporting that the binary is behind is the fourth thing that earns a verb, and `canon upgrade` is the only one mutating the machine rather than a project. It reads the manager off the install path in `src/version/manager.ts` rather than guessing from `PATH`, names what it matched first, and refuses a path under no install tree. Reinstalling over a clone is what that prevents.
- It refuses a second time when the manifest carries no `name`. The value reaches a global install command, so a manifest that failed to parse would install whatever sits under the placeholder, and the confirm defaults to yes headlessly, which leaves the refusal as the only thing in the path.
- The reinstall runs with the child's stdout pointed at stderr rather than inherited. A package manager writes progress to stdout, and inheriting all three streams puts that output ahead of the `--json` record on the one stream a wrapper parses.
- The skew read sits in `src/version/skew.ts` and has exactly two callers, `canon sync --check` and `canon claude skills drift`, each a moment a target already stops to reconcile. Putting it behind a catalog read was rejected: an agent runs those in a loop, so a registry round trip per read fails offline and needs a cache that is a second mechanism.
- It reports three states and never a fourth. `unknown` absorbs every failure with its reason, so `hasDrift` ignores the field and an offline machine cannot turn `canon sync --check --exit-code` red over a condition it never measured. A version ahead of the published one reports `current`, being a checkout between a release commit and the publish job rather than skew.
- `SkewReport` is a union on `state` rather than one shape with optional fields, so a `behind` report cannot exist without the version it is behind. Both fields are rendered into a line an operator reads, and an optional one renders the word `undefined` there.
- `InstalledPackage` runs the opposite way and carries both fields optional, since either is genuinely absent when the manifest did not parse. A sentinel string typed `string` reads as an ordinary value at each call site, which is what let a placeholder name reach a global install command unremarked. Optional forces the narrowing.
- `describeSkew` picks the remedy from the same detection the verb runs, because both callers run from a source checkout routinely and that is exactly where `canon upgrade` refuses. A line naming the verb unconditionally sends a contributor whose clone sits a release behind to a command that declines.
- `UpgradeRecord` carries a `message` field alongside `state`, rendered once per outcome rather than left for a caller to reconstruct from `before`, `after`, and `latest` by hand. The `current` branch reuses `describeSkew` verbatim. `.husky/post-merge` is the first caller reading `message` off `--json` rather than parsing the raw fields itself, covered in `.claude/context/development/hooks.md`.
- `message` is the one field carrying arbitrary text, since `describeSkew`'s `unknown` branch embeds a registry error verbatim. `emit` runs it through `singleLine`, collapsing whitespace and swapping a double quote for an apostrophe, because the field's one caller reads it with a shell pattern that stops at the first `"` a raw registry error can carry.
- Feature entries stay separate from this domain. They document a user-facing artifact such as the `SLIDES.md` source shape or the design token schema, which is worth reading without the CLI plumbing.

## Writing files and writing output

- A command whose stdout is the product writes the document with `process.stdout.write` and everything else with the `log_*` helpers, which are stderr-only. `canon docs <topic>` is the one command a caller captures with `$(...)`, so a single frame character on stdout would corrupt the document silently rather than failing.
- Anything that writes a file into a target routes through `copyPreservingMode` in `src/copy.ts`. `copyFile` imposes the source's mode on an existing destination, so a target file deliberately at 600, or one an earlier layer made executable, comes back at the source's mode. The bash `cp` it replaces left an existing mode alone.
- A verb that writes outside a target takes its destination as an argument. `canon claude setup` defaults to `$HOME/.claude` but accepts a path, which is the only way to cover the settings merge without pointing a test at the operator's real config. The sandbox scenario passes a sandbox-local path for the same reason.
- A preview and the apply it precedes run the same function. `planGitignore` dry-runs `mergeSections`, so the two cannot disagree. Parsing the source a second time for the preview is what lost, since the two reads drift. `govArgs` in `src/init/steps.ts` is the same shape, building both the `gov install` argv and the command a `--skip governance` notice tells the caller to paste.
- Machine-readable output goes through `JSON.stringify` rather than a `printf` template. Interpolating a name straight into a JSON string literal emits output a consuming skill cannot parse as soon as the name carries a quote.
- The reporter shapes the emitted record rather than the result interface behind it, and the two differ in field names. `ArchiveSuccess` in `src/tasks/archive.ts` carries `stem`, and `recordFor` in `src/commands/tasks.ts` emits that same value as `task`, so a body or a reference documenting the record off the interface names a field no caller receives.
- A record folder resolves at two roots rather than one, through `recordDir` in `src/record-root.ts`. `.canon/<folder>` is read first and `.claude/<folder>` second, and a folder neither root carries resolves to the creation default, which is `.canon/`. The read order and the default agree, which is what the move changed. They disagreed on purpose before it: the fallback shipped in a release ahead of the move it exists for, so the binary a session already held knew where to look by the time a tree relocated, while creating under the new root while its ignore line had yet to reach a project would have written records to a root that project still tracked.
- No call site spells a record root. A path composed by hand resolves against one root and reports nothing when it is wrong, which is the quiet failure the ordering exists to prevent, so a read goes through `recordDir`, a containment test through `recordDirs`, which names both roots whatever is on disk, and a write through `creationDir` or `creationRel`. The scratch folder is the one name that differs by root, spelled `.canon/tmp` and `.canon/tmp`, and the resolver owns that spelling so no caller carries a variant of its own.
- The backup is the one caller resolving the root rather than a folder under it. `workTree` and `recordsGitDir` in `src/records/backup.ts` both read `recordRoot`, since a history opened at one root beside a work tree at the other stages the deletion of every folder a move relocated and pushes it.
- A verb editing shared session scratch under a record root resolves that root through `mainWorktreeRoot` rather than the working directory. The task record verbs, `canon intake answer`, and every `canon teach` verb share the reason: every worker runs in a linked worktree where the file-editing tools refuse a main-root path and the stream editors this repository bans are what a shell route reaches for, so the write has to resolve the root in-process.
- A verb reading a tracked tree resolves `currentWorktreeRoot` instead, so it answers about the checkout the caller edited. `canon records validate` splits both ways on `isSharedScratch`, since four of its kinds read gitignored folders that live at one root and the fifth reads the standards corpus, which every worktree carries its own copy of. A default keyed on a property every member shared is the thing to re-test when a member arrives without it.
- A verb landing several edits in one file takes the whole batch in one invocation rather than one call per edit. `canon intake answer` scopes a call to a single cluster for that reason, and `canon teach glossary` writes one workspace's terms the same way, since concurrent calls read the same file and the last write keeps only its own change. A repeatable flag carrying `<key>=<value>` is the shape, splitting on the first separator so a value carrying its own survives, which is what lets `canon teach resource` take a URL holding a query string.
- A verb editing a markdown list in place groups each bullet with the indented lines wrapped under it rather than keeping the lines that open with a bullet marker. Filtering by line drops every line of a wrapped entry but the first, and the loss is silent rather than a failure, which is how `canon teach glossary` reached a sandbox fixture carrying a wrapped entry before anything caught it. `bulletRange` in `src/teach/workspace.ts` ends the span it rewrites at the last bullet or indented continuation, so an unindented paragraph written under a list stays outside and is neither sorted nor moved.
- The shape a validator walks is declared once by the module that writes it. `src/records/validate.ts` imports the workspace filenames, the subfolder names, the folder pattern, and the mission heading whose list is read as exit criteria from `src/teach/workspace.ts` rather than restating them, so the writer and the check cannot disagree on a filename and a layout change lands in one module. The heading moved to an equality test against that constant when the reader arrived, since a validator matching a spelling the reader cannot find would pass a mission whose criteria read as empty.
- A repair for a validator finding lives beside the check rather than in a fifth migration skill. `src/records/migrate.ts` holds one transform per repairable finding, keyed off `Finding.remedy`, and re-reads the file rather than trusting a value the validator computed, so a check and its repair cannot drift apart across an edit. The four migration skills move a target project's content through a session's judgment. This row rewrites a gitignored records folder in whatever repository holds it, a mechanical rewrite with no judgment call left for a session to make, which is what the task's own outcome asked for.
- A transform ships only where the missing value is recoverable from the record itself. `migrateRecord` repairs a memory entry's missing `category` from the filename prefix `checkMemory` already derives it from, and refuses a missing `title` or `description`, since neither is a value the file carries anywhere else. `canon records migrate` writes nothing until `--write` is passed, matching the contract `canon tooling sync` carries: naming a record kind is not consent to rewrite every record inside it.
- The read and write batches in `canon records migrate` run under `Promise.allSettled` rather than `Promise.all`, each turning a rejection into a per-record refusal instead of aborting the batch. `program.parse()` in `src/cli.ts` carries no top-level catch, so a batch that rejected as a whole surfaced as a stack trace on a record that had already written to disk, rather than the structured refusal every other refusal path in the file returns. `migrateExitCode` reads `repaired` rather than a raw finding count for the same reason: a candidate whose transform later refuses is a record `--write` cannot help, so it exits 1 rather than the 2 that promises a write has something to apply.
- `canon records ordinal --claim` (`src/records/ordinal.ts`) serializes two record kinds sharing one ordinal sequence, `intake` and `groundwork`, closing the race that gave two sessions the same number for two different folders the same day. A leaf `mkdir` on the kind's own folder is not enough by itself, since the two kinds' leaf directories never share a path and so never collide with each other. The verb reserves the number first, at a path both an `intake` claim and a `groundwork` claim resolve to identically regardless of kind, and only creates the kind's own leaf folder once that reservation is won, retrying past a losing reservation up to a fixed bound before refusing as `ordinal-contended`.
- `canon migrate rename` is the second verb under a records-shaped contract and the first whose corpus is the repository itself. It holds the token map, the protected forms, and the exclusion set in `src/migrate/`, reports until `--write` is passed, and takes a `--scope` of `self` for every tracked file or `target` for the toolkit-owned folders alone, where the second reports what it declined to touch as citations rather than rewriting prose a project wrote. What the exclusion set holds is not a preference: the tool's own token map, the tests naming both spellings, the changelog, and the eval transcripts each state something _about_ the rename rather than using the old name, and rewriting any of them destroys what it is for. A second run over an already-renamed tree rewriting zero tokens is the check that the set is complete, since a non-zero count names exactly what is still unguarded.
- The engine behind that verb takes its map, its protected forms, and its exclusion set as a rules object rather than reading module constants, so `src/migrate/` now compiles two presets and `canon migrate skill-names` runs the second. What separates them is what each token is: `aitk` is a word stem that legitimately carries a suffix, as in `aitk-allow-superseded`, and a skill name is a whole name, so only the second asks the scanner to stop where the word ends. Running the skill preset without that boundary moved `wiki/claude/claude-worktrees.md`, a page about the harness feature sitting in a folder where every sibling is named for a Claude Code concept, and rewrote sixteen citations of it. The ordering of the alternation is reported as `tokenOrder` for the same class of reason: `plan-intake` sits inside `plan-intake-answer`, and both rows land on a name opening with `plan-intake`, so reading the ordering off the rewritten string reports a pass whichever way the alternation was built.
- Both presets emit their record to stdout before `applyRename` runs, so a caller piping stdout into a truncating reader kills the process between the two. The record reads `wrote: true` with the full file, move, and rewrite counts, and the tree holds a partial apply: observed at 2 files changed out of 273 against a record claiming all 273, recovered by resetting and re-running with nothing on the other end of stdout. Reporting ahead of applying is the contract rather than a defect, since the record describes the plan and a dry run has to emit the same shape, so what is exposed is the pipe. Redirect the record to a file or let it reach the terminal, and never read it through `head`.
- A verb exists where an instruction to the model would reproduce a defect the instruction already failed to prevent. `canon teach lesson` draws quiz option order rather than telling a session to vary it, because an author varying position by judgment settles on the first slot. It writes nothing: it reports the numbered path the lesson takes, the shared stylesheet with whether the file is on disk, the mission's success lines, and one draw per question. Reporting the stylesheet rather than writing it is what keeps the second lesson in a workspace from discarding what the first one put there.
- `canon teach nav` extends the same principle to a whole page's chrome, splicing the header, breadcrumb, jump menus, and behavior scripts from four marker comment pairs a session leaves empty rather than composing them by hand, which is the judgment that let three hand-authored pages drift out of step with each other. A lesson missing a marker pair is refused by name rather than guessed at, and the root listing and every contents page rewrite from the same read.
- A page behavior a stylesheet can carry ships as CSS spliced into the lesson rather than as an injected script. `canon teach nav` gates a quiz on `:has()` over the radio inputs each question is written from, hiding every question that follows one holding no checked input and hiding feedback until its own question is answered, all inside `@supports selector(:has(*))` so an engine without `:has()` renders every question rather than a stepper showing nothing. Showing feedback unconditionally outside that wrapper would complete the degradation and was reverted after a driven read, since the rule outranks `.fb { display: none }` on every engine and reveals the feedback in the button-shape lessons the retired script still drives. The block is spliced after the workspace stylesheet so it wins the cascade at equal specificity, and it hides and shows and sets nothing else, which leaves layout and appearance to the workspace. One detector on `<button class="opt"` decides both regions rather than the scripts one alone, since the stepper's rules match a button question that can never hold a checked radio: a lesson given both mechanisms hides every question past the first for good and outranks the class `QUIZ_SCRIPT` reveals feedback with. Adding the CSS unconditionally and gating only the script was the design until a browser was driven against both shapes, and nothing short of that read reaches it, because the markup is valid, the splice succeeds, and the page renders. The question gate takes the general sibling combinator rather than the adjacent one, which selects the same set for a conforming quiz and is what keeps the gate from resting on a markup contract nothing checks, since the adjacent one matches nothing the moment anything sits between two questions and shows every later one at once.
- A drawn order reports the position it produced alongside the permutation. A caller handed only the permutation derives the answer index itself, which is a second place the same fact can be got wrong, so `orderQuiz` returns both and no caller computes either.
- A reader over a prose corpus counts what it cannot answer apart from what it can. `canon intake list` reports an item carrying no answer slot separately from unread and answered, because folding it into either one hides a malformed file behind a number that reads as work remaining or work done.
- A folder identity gaining a prefix does not break the argument callers already type. `matchSlug` in `src/intake/folder.ts` tries an exact match against the bare argument first, then the one entry whose name is an ordinal ahead of it, so `canon intake list toolkit-overview` keeps resolving once the folder becomes `21-toolkit-overview`. Every outcome reports `basename(opened)` rather than the caller's own argument, so `list`, `list <slug>`, and `answer <slug>` name the folder the same way in `--json`.
- A suffix match that finds more than one folder is a collision, not an absence. `matchSlug` returns a discriminated `SlugMatch` rather than `string | undefined`, so `openFolder` refuses `ambiguous-slug` naming every match, distinct from `no-folder`, which is what lets a caller tell a typo from two dumps sharing a topic.

## Prompts and unattended callers

- Declining a prompt exits 0. A cancel is a deliberate choice rather than a failure, and `runDomains` in `src/init/run.ts` reports any non-zero domain as `Failed, run manually`, so exiting 1 made `canon init` announce a broken install for work the operator chose to skip. Apply it to any prompt a port carries over.
- A headless run refuses to write to a git remote. The domain syncs still apply, so headless keeps everything but the push. It is the judgment the retired standards refusal made, applied to an action that reaches further outward than a local overwrite.
- The refusal covers a remote the caller did not name. `canon records push` writes to a remote from `.husky/post-merge` with no prompt, because a person configured that remote by hand and the verb refuses until they have. What the sync refusal protects against is a push nobody asked for, so a verb whose entire product is the push is outside it and gates on the configuration instead.
- A picker standing in for a required argument refuses headlessly rather than defaulting to its first option. Confirm-then-apply prompts keep `nonInteractiveDefault`, since the caller already named what to apply. The distinction is whether the prompt is choosing what to do or confirming what was asked for.
- A branch gated behind a prompt takes an optional decision seam so a test can reach it. `select` exits without a TTY, so the branch behind it is otherwise reachable only by driving a PTY. `WorkflowDeps.choose` defaults to the real prompt, leaving production behavior unchanged while the tests assert the exact staged set. Prefer this over asserting on the logic that feeds the prompt.
- A command an unattended caller drives makes every gate a refusal with a non-zero exit. `canon tasks archive` is called by `.husky/post-merge` and by `task-board`, and a gate that only reports is useful to the second and worthless to the first. The command owning the gates is also what keeps the two callers from drifting into archiving differently.
- A non-zero exit reaches the hook reliably and reaches a session only sometimes. An operator's shell profile may wrap `canon` in a function that runs the binary and then a second command and takes the second status, measured against `0.98.0` masking an ordinary refusal and an unknown command alike.
- Nothing inside the process can see that function, so no probe here detects it and the remedy sits entirely in what a caller reads. A verb a skill drives therefore owes a `--json` record carrying whatever the caller routes on, which is `ok` and `reason` where the verb refuses and the per-item actions where it reports, and the skill body branches on the record.
- Nothing gates on a body reintroducing an exit branch. A pattern matching one fires on every legitimate use, which is the false-positive class that teaches contributors to route around a stage, so the rule stays stated and gets revisited if a second instance appears.
- The seeded `CLAUDE.md` names no `canon` verb, and the one seeded hook that calls one already decides on the record. A scaffolded project inherits no exit branch to correct, checked on 2026-08-20.
- A refusal reason splits on whether the caller can act on it, once any caller is told to swallow a subset. `git-pr` skips silently on `no-board`, `no-match`, and `ambiguous`, because each describes a board where a guessed write lands on the wrong task.
- A malformed argument describes the command line instead, so it refuses as `bad-input` and falls to that skill's report branch. Sharing a reason across the two classes puts a caller defect inside a swallowed set, which is the silent loss the verbs exist to prevent.
- All three task verbs carry that split, not only the two a swallowing caller drives. `archive` answered both selectors with `ambiguous`, which routes `task-board` to repair a task citation that is fine, so one mistake read as three different board defects depending on which verb saw it.

## A verb whose subject is gitignored walks the tree instead of asking git

`listRepositoryFiles` is what every sweep in `src/migrate/` reads, and it answers about tracked files, which is the one population `canon migrate record-tree` has to miss entirely. The record folders are gitignored by construction, so that listing returns none of them and a verb built on it reports a clean tree over the 2,636 old-root citations the records were actually holding. `walkRecordTree` reads the record root with `readdir` and `Bun.Glob` instead. That is what makes `src/migrate/record-tree.ts` a sibling of `records.ts` rather than a scope flag on it: one module answers about a repository listing and the other about a directory walk, and folding them would give one file two enumeration models.

Asking git for the ignored half, with `--others --ignored`, was the alternative. It returns the backup history under `.canon/.records.git` along with everything else, which `runRecords` already measured for this tree at 9,744 files and 83M, so the listing pays to enumerate an object store before anything filters it back out. The walk skips that directory by name and never opens it. Measured at `d60b3117` on 2026-09-01.

## A verb reading both records and a git range takes two roots

`mainWorktreeRoot()` is the right root for a records read and the wrong one for a git range, and a verb doing both has to hold them apart. The plans folder, the board, and the memory pen are shared scratch at the main worktree root, while a dispatched branch's own commits live in a linked worktree, so one root answers both questions only in the main checkout. `canon tasks plan-reach` carries the split as `ReachOptions.repo`, defaulting to the records root and set by `runReach` to `process.cwd()`, which is the worktree the caller stands in. A single root there measures a checkout sitting on the trunk: the range closes on itself and every branch reports having written nothing, which is a clean answer rather than a failure and so reaches a reader as a result.

`canon gov test-order` has the same shape and answers it in prose instead, with `auto-ship` Step 4 telling the session which directory to run it from. A parameter is the stronger form, since an instruction is only as good as the body holding it, but the two are not equivalent surfaces: that verb takes its root from where it was invoked and has no records read to part company with.

## An argument added for testability widens the guards

Turning a hardcoded path into an argument for testability widens the input domain, so the guards need re-auditing against what the argument now admits. Giving `canon claude setup` a `[dest]` argument let the settings merge be covered without pointing a test at a real home directory. The guard had to be added by exact path rather than by prefix, since the sandbox scenario legitimately writes under the repo.

## A verb driving an external tool measures it rather than reasoning about it

`canon worktrees reclaim` is shaped by two behaviors read off git 2.43.0 rather than assumed. `git worktree remove` takes a registration whose directory is already gone as readily as a live one and clears it, so the hand-deleted case needs no command of its own and the sequence is one unlock, one remove, and one branch delete whatever state the directory is in. The plan reasoned the opposite way, that `remove` operates on a directory that exists, and a probe against a throwaway repository is what separated the two.

The same command removes the directory a caller is standing in without complaint, which is the second reading and the one that decided a guard. `verdict` in `src/worktrees/reclaim.ts` refuses the worktree the reading runs from, and `runReclaim` scopes every git call in the removal to `mainWorktreeRoot` rather than to the caller's directory, since a removal earlier in a run would otherwise delete the directory the calls after it resolve against and leave each remaining branch undeleted while reporting the failure against the worktree rather than the cause. `RemovalOptions.cwd` carries no default for that reason, which is the one case in this domain where a required argument beats a safe one: the only value a default could hold is the process directory, and that is the unsafe half, so a caller that omits it meets a compiler error rather than the failure.

`git worktree prune` stays in the sequence as the recovery for a git that refuses `remove` on a stale registration, and it runs once between the removals and the branch deletes. It takes no path to scope it, so it clears the bookkeeping for every directory already gone, refused entries included, and a run placing it after the branch deletes would leave a branch standing with nothing left in the listing to find it by. `git worktree unlock` exits 128 with "is not locked" for the ordinary case, so its result is not read and a lock that genuinely refuses to lift surfaces as the remove failing instead. Measured at `69f9db56` on 2026-09-01.

## A record a shell reads orders its fields for the pattern rather than for the reader

`canon worktrees reclaim` carries a `--json` record, and `.husky/post-merge` is its first caller that is not a person. The record is `{reason, detail, dryRun, reclaimable, removed, failed, pruned, outcomes}`, and that order is load-bearing rather than cosmetic. A shell reads it with a greedy `sed` pattern rather than a parser, so `reason` sits ahead of the free-text `detail` a second match could otherwise be found in, and the scalar counts sit ahead of `outcomes`, whose per-entry `failedAt` and boolean `removed` match neither digit pattern. `src/commands/worktrees.test.ts` asserts the ordering, since a field reordered by a later edit breaks a caller no typecheck reaches.

`reclaimRecord` is a pure function over the values the run already holds, which is what makes the record testable without a repository, a `gh` credential, or a directory the test would then have to remove. `migrateExitCode` in `src/commands/records.ts` is the same shape. The counts derive from `outcomes` inside it rather than being passed in, since two numbers a caller computes are two numbers a caller can get wrong.

A dry run and a reading that found nothing reclaimable both carry `removal: null` on the source and differ on `reclaimable`, which is what lets a caller separate a quiet repository from a run that was asked not to act. The failure path no longer returns early either: one `emitReclaim` call serves both endings and the exit became `failed.length > 0 ? 1 : 0`, so no ending can ship without its record. ## A verb answers about a commit rather than about the object naming one

`canon pr head` and `canon pr checks` both resolve the branch tip through `git ls-remote` and key what they report on that sha. `gh pr view --json headRefOid` reads a field on the pull request object, which trails the branch ref by up to a minute after a push and says nothing about the trail, so a reviewing session called a pushed commit unpushed on `#1341` and a worker fired a retracted green claim on `#1340`, both on 2026-09-01 off that one field. The remote rather than the remote-tracking ref, since a tracking ref is only as current as the last fetch and the push worth catching is the one the process never saw. It costs roughly half a second against 0.001s for the local read, sampled at 0.41s, 0.55s, and 0.67s across two days, on callers that already spend a `gh` round trip on the same line. `docs/agents/pr-reads.md` carries why that spend is right in the orchestrator poll and wrong in `canon targets pulls`, which is a question about what each reading decides rather than about what it costs.

`canon pr review-state` is the third verb under `pr` that exists because a GitHub field answers a different question than the one a caller is asking. `commit.oid` and `submittedAt` on a review are stamped at submission, so a push landing between a pass's read and its post moves both onto a commit that pass never opened. `review-pr` writes the commit it read and the instant it read it as an HTML comment on the last line of every body it posts, and `src/pr/review-scope.ts` parses that marker off the newest pass in the review family, falling back to the two stamps for a pass posted before the mechanism shipped. `source` on the record names which answered, so a caller can tell a read-time reading from a stamped one.
