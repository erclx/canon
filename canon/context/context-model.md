# Context model

## Overview

Cross-domain design doc for how a project splits agent context across loading tiers, and the operating manual for `canon/context/` itself. It governs every entry in this folder rather than describing one domain, so it sits alongside them rather than inside any one. It stays one file past the length checkpoint because `canon/ARCHITECTURE.md` cites its path for three decisions, and every section answers the same question of where a fact belongs.

Target projects scale by splitting context across three loading tiers:

- Always loaded: the root `CLAUDE.md`, `canon/REQUIREMENTS.md`, and `canon/ARCHITECTURE.md`, eager at session start, holding cross-cutting behavior, product scope, and project-wide invariants
- Path-scoped lazy: `.claude/rules/<scope>.md` with `paths:` frontmatter, loaded by glob match when files are read, holding do and don't rules and naming conventions for a file scope
- On-demand lookup: `canon/context/<domain>.md`, `canon/wireframes/<surface>.md`, and `.claude/wiki/<page>.md`, read when the domain or surface is touched, holding per-domain narrative, per-surface layout intent, and tooling or workflow reference, indexed for discovery

`canon/context/` exists for discoverability rather than load cost. A nested `CLAUDE.md` below the cwd loads lazily when its subtree is read, so it is already cheap, and what it lacks is any signal that it exists. The `index.md` catalog lists every entry up front, so a session picks the one it needs before touching the domain.

## Layout

Flat by default: one `.md` per domain (`canon/context/web.md`, `canon/context/api.md`). Use a folder (`canon/context/<domain>/<sub-area>.md`) only when a domain has 3+ sub-areas that don't fit cleanly in one file. The indexes system handles nested folders natively. <!-- audit-ignore-citations: canon/context/web.md, canon/context/api.md -->

`canon/context/index.md` is regenerated by `canon indexes regen` from each entry's `title` and `description` frontmatter. Do not hand-edit it.

`standards/context.md` carries the rules on entry shape. Its `## What a working entry looks like` section is the criterion the shape rules serve: an entry works when a session can answer where things live, why they are that way, and how to add one more, without opening source.

## Decisions

### Which tier a fact belongs in

A fact goes to `.claude/rules/` when it fires on a specific path being edited and violating it ships silently, and to a context entry or a skill body otherwise. Recording it in an entry's `## Gotchas` reaches too little, and eager loading does not substitute: a rule delivered at session start competes with the whole file, while a glob-matched one arrives attached to the action. The test rejects most of what it is run over, because a rule per gotcha rebuilds the `CLAUDE.md` the tiers exist to prevent.

Firing is one axis of three. The second is conditional presence, which a rule buys and a line in `CLAUDE.md` or a seed cannot, since an eager line loads into every session. The third is updatability, which is what makes `governance/rules/core/` correct as rules for the fifteen of its nineteen rules carrying no `paths:` glob: a rule installed through governance sync carries a later fix to every project that installed it, where a seed line stays fixed at the scaffold it was written into. Measured at `5196cc9a` on 2026-08-27.

The test ships as `governance/rules/claude/592-claude-md.md`, attached to an edit of the root file in every target that installed governance. A project scaffolding without governance is reached by neither surface, since the seed does not state the test.

### What each root holds

The project root splits three ways: `.claude/` holds what Claude Code reads by path, `canon/` holds what the toolkit authors and commits, and `.canon/` holds every gitignored session record. One ignore line covers `.canon/`, so a record folder added later needs no row here, no ignore entry, and no manifest edit. `canon/ARCHITECTURE.md` carries the two tests and the alternatives they beat.

Five surfaces under `.claude/` are Claude Code's own, and the toolkit invented none of them:

- `.claude/settings.json`, which registers the hooks
- `.claude/settings.local.json`, per machine and untracked
- `.claude/hooks/`, run on the events `settings.json` names
- `.claude/skills/`, the internal skills a session in this repository can load
- `.claude/rules/`, glob-matched against the path being edited

Two more sit under `.claude/` as the harness's rather than the toolkit's. `.claude/worktrees/` is where `EnterWorktree` creates a worktree and requires its target to sit, and nothing in this repository names `.claude/scheduled_tasks.lock`.

The toolkit's committed surfaces sit under `canon/`: `canon/context/`, read on demand through its catalog, `canon/config/`, holding `baseline.json` for `canon audits` and `pr-labels.toml` for the pull request label map, the two eager documents, `canon/DESIGN.md`, read by `canon design render`, `canon design board`, and the design skills, and `canon/wireframes/`, audited by `canon context` in a project that carries one. The install stamp and the audits baseline sit at `canon/config/` behind the same read fallback the rest of the corpus carries, since neither is a file Claude Code loads by path.

`.tmp/`, when it exists, is the scratch rule's gitignored fallback spelling, carried for a project the record move has not reached and retired once `canon migrate records` has moved the last one off it.

### Migrating a project onto the roots

`canon migrate records` moves the gitignored record folders under `.canon/`, a filesystem act no commit records, since every folder it moves is untracked. `RECORD_ROOTS` resolves the old root behind the new one, so a target on an older binary keeps reading either root, and `CREATION_ROOT` names the new root for anything created. Shipping the resolver and the move together was declined, since it would strand a target on an older binary reading its records at a root its CLI does not know.

`canon migrate surface-roots` relocates the committed surfaces with `git mv` and rewrites their citations. The cost is a tracked `canon/` sitting one character from the ignored `.canon/`, which a reader skimming a path cannot tell apart.

The bare `.canon/` ignore spelling is what keeps a carve-out out of reach: written as `.canon/*`, `!.canon/x/` would stage `x/`, while an unnamed new record folder stays ignored either way. Nothing enforces that the spelling stays bare. Keeping the old ignore entries until every recorded target reported migrated, and gating the collapse on the target index in `src/targets/registry.ts`, were both declined for the single line.

### How entries get populated

`docs-fold` runs at ship time through `git-ship` or `auto-ship`. It reads the diff, maps changed files to the entries that reference them, flat `canon/context/<domain>.md` or a nested domain's `canon/context/<domain>/index.md` and its siblings, and rewrites the affected sections from the diff. `docs-sync` follows the same pattern for the README and `docs/*.md`. It runs at ship time rather than plan time because the plan describes intent and drifts during implementation, while an entry should reflect what was built.

New entries are not created automatically, since auto-creation pads the catalog with low-signal entries refreshed every pull request. Create one by hand following `standards/context.md`, and `docs-fold` keeps it current after. The rule does not reach the tooling stacks, which ship `development.md` and `ci.md` as user-owned seeds under `tooling/base/seeds/canon/context/`, arriving filled rather than generated, a decision `tooling/base/reference.md` owns. Check both seed sources before concluding an entry is absent from a scaffolded project.

Mapping changed files to entries misses two shapes, both produced by a change that removes a capability, and the `docs-fold` body holds the sweep that catches them. The first is the half-rewritten entry, refreshed at the top and left alone below, where the current opening lends authority to the stale remainder. The second is a sentence a change inverted from a distance: a claim comparing two surfaces stays true only while both hold, and its file often sits outside the diff. Rewriting only what the diff touched stays the default, overridden only inside an entry the run already edited.

## Gotchas

### A folder split is a ceiling rather than a fix

A split child re-accumulates content past the checkpoint the same way the flat entry did, and `standards/context.md` names no split as a length remedy on its own. It asks three questions past 150 lines: whether the entry still covers a single domain, whether it has filled with content a command reproduces, and whether it carries its own history. Split only when the single-domain check fails, since a task filed as a split on line count alone has skipped the diagnosis.

Measured 2026-08-05 with `canon context audit`: 22 of 48 audited entries sat past the checkpoint, and 14 of those were already sub-files of folders that had split.

### A weight remedy grows the file

Both remedies for a weight finding make the file longer. Collapsing heavy bullets into prose costs a break wherever the prose crosses the paragraph checkpoint, and a subheading breaking a long run costs about three lines, so the depth measure can improve while the length measure moves the other way. Report the post-remedy length as the number a folder decision is made against.

Projecting a split child's size from the source entry's section weights undercounts it, since the flat `## Decisions` and `## Gotchas` blocks distribute into children by topic and that arithmetic never counts them. Distribute first, measure with `canon context audit`, and fix the file shape after.

### What a split strands

A reader enumerating a flat surface pins depth somewhere, so converting an entry to a folder can drop it from that reader's output rather than erroring. `listTopics` pins it through `new Bun.Glob('*.md')` in `src/docs/read.ts`, and `list_text` through `find -maxdepth 1` in `scripts/docs/list.sh`. `bun run check` passes regardless, since every stage tests the files that exist rather than the names a command can reach. `internal/rules/claude/598-authoring-layout.md` carries the depth rule for four installable roots, and `canon/context/` and `docs/` sit outside it, so count the roots inside each reader before splitting either.

A sub-area file resolves by its bare name once every root has been tried for a sibling file and for a folder, and only where a single folder across both roots carries that name. Reading depth last is what keeps a widened reader additive.

A split strands three classes of reference no gate reads. An entry's own direction words dangle, since the citation gate resolves backticked paths and a bare `above` names none. A finding pinned to `<entry>:<line>` stops resolving while its task still ships. Every root-relative link leaving the moved file deepens by one segment, and `canon context audit` reports nothing about the depth a path was written at. Grep for `above`, `below`, and the entry's own heading names before splitting, count the links leaving the file, and re-resolve every open line-pinned finding after.

### What earns a line in an always-loaded file

A document is always-loaded only when an `@` line in `CLAUDE.md` names it. Nothing gates the toolkit's own `CLAUDE.md` against the seed it distributes, `tooling/claude/seeds/CLAUDE.md`, so grep `^@` in `CLAUDE.md` and diff the anchor block against the seed before calling a document always-loaded. An `@` line carries a catalog or a short document every session needs, such as a folder `index.md`, while a lookup file such as `canon/DESIGN.md` stays a one-line key path.

A line stays in either `CLAUDE.md` only when no always-loaded core rule, no path-scoped rule firing at the moment it matters, no eager import, and no catalog already carries it. A path-scoped rule fires on edit rather than during planning, so a design principle a command is planned against stays in the root even where a rule on `src/` restates it. The seed keeps a line a core rule duplicates when a target installing it without governance would otherwise lose the instruction, which is why the seed keeps its Context bullet.

The root file keeps its own folder map. The context standard's cap on re-derivable structure governs a second copy inside a per-domain entry, where the reader has already arrived. The root map orients a reader who has opened no entry yet, and a pointer into the catalog costs the discovery hop the tier split exists to remove.
