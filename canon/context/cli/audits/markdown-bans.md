# Markdown audit

## The ban scan and its gate

- `canon markdown audit` is the first verb that reads a ban list rather than measuring structure, and the first that needs no folder to resolve. An attribute standard governs a file, so requiring the index-plus-entry contract was what kept `.claude/rules/` and `governance/` outside every audit the toolkit shipped, which was 90 markdown files across three trees when the since-retired `snippets/` was the third.
- The ban set ships in `src/markdown/bans.ts` and the nine checkpoints in `src/markdown/structure.ts`, rather than being parsed out of the standards per run. Parsing was the original design and it put a parser contract on documents authored for people, which the standard had to carry a paragraph of its own to protect: a one-word backticked example in a `- Do not use ` bullet was lifted into a literal ban set and banned that word everywhere.
- Six of the nine checkpoints are stated in `markdown.md` and the three cadence numbers in the `write-human` skill. That split is the content boundary rather than an inconsistency, since the standard carries what a scan decides and the skill carries what a ban list cannot express.
- Nothing compares the shipped numbers against the sentences stating them any more, and that is the accepted cost of ending the parse. A checkpoint moved in code and left alone in `standards/markdown.md` drifts silently, so move both. Re-establishing the comparison in a test would put `markdown.md` back under a machine reader and undo the unlock.
- The set is closed rather than extensible, and it holds the two characters alone, since a character is the one class a literal match settles. A project wanting its own vocabulary is asking for a different feature.
- Words and spellings sit outside the gate. Word guidance lives in the `write-human` skill, because a word ban catches the token and misses the habit, and `just`, `allows`, and `very` carry honest uses no literal match separates. Spelling belongs to cspell, whose base seed already reads every word. Gating both was the rejected alternative, since a word set is a prior an author already knows rather than a filter that catches anything: measured at `60fc97bf` on 2026-08-19, 21 terms ran across 483 markdown files for a clean exit, and every occurrence of a banned word sat inside the ban list itself or inside an example demonstrating the ban. `centre` has no check, because the base cspell seed accepts it.
- An empty set is reported rather than passed. It finds nothing and would exit clean, which reports a corpus nobody checked as a corpus carrying no violation, so `emptyBanSets` names the set when it arrived empty and the run exits 3. The set ships with the package, so the only cause left is a defect in the build.
- That code is separate from the refusal at 1 because the push stage answers them differently. A refusal built no corpus and the gate reports the stage as unmeasured, while an empty set walked the corpus and looked for nothing, so the stage fails on 3. Reusing 1 put the whole gate behind a warning that lets the push through, which is the pass the outcome forbids.
- The `--json` record carries `bans.emptySets`, and both hooks read that field.
- Both hooks also answer an absent record, which is the hole the seed's move onto the verb exposed. A completed run always writes the record and a refusal writes none, so emptiness means the verb declined to measure rather than measured and found nothing. The verb refuses outside a git repository, which a scaffolded project can be, and reading the findings alone reported that as a clean file.
- This repository cannot observe the fallback through an ordinary run, since the package root resolves to the repository root here and `standards/` is already the second root. A fixture rooted outside the repository is the only place the third root is reachable, which is what `src/standards/read.test.ts` and the `loadStandards` cases in `bans.test.ts` each root at `mkdtemp`.
- `PROJECT_ROOT` derives from `import.meta.url` rather than Bun's `import.meta.dir`, which the test runner leaves undefined. Any module reading the package root is otherwise unreachable from a test, whatever the module does with it.
- Fence parity is the second false-positive class and the fix is shared. A walker toggling on any backtick run reads the closing fence of a ```block nested inside a ```` one as an opening and inverts the rest of the file, which reported ten closing fences as bare.
  - `src/markdown/scan.ts` owns the only fence walker, marking each line rather than filtering it, since the depth measure skips a fenced line, bullet folding treats one as a break, and the ban scan ignores it
  - `src/records/validate.ts` reads its `linesOutsideFences` from there rather than keeping the second copy it had
- Frontmatter is the third class and the anchor is what settles it. The pattern matches at position 0 alone, so a `---` block inside a fenced template is body rather than a second divider.
- The ban scan and the weight measures disagree about what a reader sees, which is the design rather than a defect. Both drop a link destination and an autolink. Only the ban scan drops a code span, so a standard quoting its own banned character does not report itself, while a weight measure counts a backticked path because the path is on the page.
- The two therefore share the span patterns and not the masking function. `maskDisplayed` holds each span's width so a finding can name a column, and a held width is what a weight measure exists to discount, so `visibleText` drops the span. Measuring source cost 7 weight-only paragraphs and 4 files past the depth checkpoint.
- `visibleText` walks around a code span rather than through it. Keeping the span counted and then dropping link or autolink syntax from inside it takes the decision back, and a backticked path holding an angle-bracket placeholder is where that lands. Masking through one hid 2 bullets and 5 paragraphs the corpus does carry.
- The ban half gates and the structural half reports, which is the corpus deciding rather than the measure. A banned character is a fact and passes the test that gates a citation, so what held the gate back was that failing on day one against a corpus never checked mechanically fails on work nobody has had a chance to fix.
- Taking the ban count to zero is the precondition a gate reads. The structural measures at 99 heavy bullets, 220 heavy paragraphs, and 40 files past the depth checkpoint are no gate's business and moved with neither decision.
- The gate exits `2` and leaves `1` meaning the refusal it already meant, so a measurement that found something stays distinct from the audit declining to measure. `src/markdown/gate.ts` takes the structural reports beside the ban list and gates on the bans, which is what gives the split a place to be asserted rather than a signature that states it in prose.
- A relative link resolving to nothing on disk joined the ban list as a second gating fact, over the same corpus. `src/markdown/links.ts` classifies a destination and skips one carrying a URL scheme, a same-file anchor, a root-absolute path, or a template placeholder in angle brackets, so `<slug>`-shaped illustrations stay unreported. `gate.ts` gates on either list, and `src/gate/measures.ts`'s `markdownBans` reads the shared exit code rather than a second `Measure`, since the audit already reports both facts under one run.
- The merge gate in `src/gate/stages.ts` runs the gate over the whole corpus rather than the changed files, because a `Do not use` bullet added to a standard bans a token retroactively and no file in that push was edited. The stage sits below `Context citations` for the reason that one carries: every stage above it is pure bash, and both of these depend on TypeScript.

- The corpus comes from the tracked listing and the walker opens each path without testing that it exists, so a tracked file deleted in the working tree with the deletion unstaged throws `ENOENT` rather than reporting. Stage the deletion before auditing a change that removes a file.

## Why the ban gate reads one rule set for every path

`canon context audit` tiers by path, failing a push against a seed tree and reporting against a context entry, and it carries the `stub: true` exemption for a section a standard sanctions omitting. `canon markdown audit` has neither half. Every markdown file git lists is measured the same way, and nothing under `src/markdown/` reads an exemption marker.

Tiering fits a structural measure because a checkpoint is a judgment, and a seed leaving the repository is where a judgment is worth failing a push over. A closed set has no such gradient. A banned character is as wrong in a context entry as in a seed a target installs, so a per-path tier would rank the tree its own authors read most as the tree where a violation counts least. Adding that tiering is the change this record exists to decline.

## The edit-time hook

- `.claude/hooks/standards-audit.sh` calls the verb per edited file, so one copy of the ban set serves the surface an author meets at edit time and the stage that fails the push. A second copy of the set inside the hook is a divergence nothing would compare.
- The hook decides from the `--json` record rather than the exit code, so a binary predating the gate reports at edit time all the same. A missing runner degrades to a report of no enforcement rather than to silence, since an edit nobody checked and an edit carrying no violation are the same quiet to a reader.
- It prefers a checkout's `src/cli.ts` over a globally installed `canon`, the choice the merge gate makes for its own reason. The two are different builds on any machine, where the installed binary trails the checkout by however many releases it has missed, so a ban kind added to `src/markdown/bans.ts` would report at push and not at edit.
- Four surfaces read the ban set and two go through the verb. `claude/skills/standards-audit/SKILL.md` greps the tokens agent-side, which is a session reading prose rather than a process it can shell out to, and it ships to every target. That one and the seed hook are where the next drift lands, since nothing compares either against the verb.
- The seed copy of the same hook calls the verb too, since the set ships as data and a hook parsing `markdown.md` itself would read nothing a ban added there states.
- A scaffolded project carrying no `canon` gets a report rather than a pass. The seed resolves one runner where the toolkit copy resolves two, since it looks for no checkout source, and it names the binary to install when neither the findings nor the empty-set field can be read. `scripts/core/check-seed-independence.sh` scopes to markdown alone and leaves the seed hooks outside its walk, which its own comment records as deliberate.
- `src/hooks-guard.test.ts` strips the real binary from `PATH` so the index hooks report the same branch on every machine, which puts the acting branch of a hook that shells out to the CLI out of reach. That case takes a stub runner on a `PATH` of its own, pinning the output to the fixture rather than to whichever build the machine carries.
- Each stub reports a `kind` naming itself, which is what lets a test read the runner the hook resolved. The acting case proves a verdict was reached and says nothing about which branch produced it, so the preference could stop resolving and stay silent with every test green.
- Three cases cover the checkout, the fallback, and the machine carrying neither, and each was confirmed by breaking its branch and watching that case alone fail
- The degradation case runs against a fixture directory linking `bash` and `jq` and holding no runner. Both are what the run itself depends on, the first to spawn the hook and the second to parse the payload before the branch is reached, and missing either lands somewhere silent for an unrelated reason that would pass the case against the wrong branch.
- Filtering the caller's `PATH` for a directory carrying `jq` and no runner was the alternative, and it reads machine provisioning rather than behavior, since a machine carrying `bun` in `/usr/bin` leaves no directory qualifying and the case fails on its own guard
