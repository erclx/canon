# Sync

`src/sync/` holds one engine that gov installs and syncs through, plus the git workflow `canon sync` runs afterward. Gov is the only adapter left, since standards and snippets both closed their install channel. The install stamp is what lets the engine tell a file the toolkit moved from a file the project edited, and `canon/context/cli/stamp.md` carries it. `canon/context/cli/sync-reporting.md` carries attribution from history and the freshness report, which reads the same plan a sync would apply.

The folder splits by job: the git workflow across `target.ts`, `git.ts`, and `workflow.ts`, the stamp in `stamp.ts`, the drift report in `check.ts`, and the history fallback in `history.ts`.

## The sync engine and its adapters

- An adapter supplies only a source lookup and, optionally, surfaces the file walk cannot see. `src/gov/adapter.ts` needs no widening the engine itself does not already offer, which is evidence `SyncAdapter` generalizes rather than describing gov alone. Treat a required engine change in a later adapter as a finding, and prefer widening the adapter interface over branching inside the engine.
- The engine's widened interface takes three optional fields rather than a branch on the domain name: `nonInteractive`, `isExcluded`, and `onComplete`. Each defaults to the behavior gov and snippets already had, so a widening could not silently change an existing adapter.
- `isExcluded` and `onComplete` default cleanly and cost nothing unused. `nonInteractive` has no declarer, so the `refuse` branch in `src/sync/engine.ts` and the `hasUnattributedDrift` it guards are unreachable rather than merely unused. Removing them is a decision to take deliberately, since the reasoning behind the extension point is recorded and would go with the code.
- The non-interactive policy is a discriminated union rather than a boolean. A headless run applies for a toolkit-owned domain and would refuse for one whose files a project edits, and the refusing variant carries its own message and hint so the engine never holds domain copy.
- `projectSubdir` on `SyncAdapter` names a top-level folder the walk orphans by location, checked in `planSync` and `recordStamp` before `locateSource` runs, so a file there is orphaned even when its name matches a toolkit source. Gov declared `project`, the name a target already reached on its own for its authored rules, until its installed root narrowed to `.claude/rules/canon/` and left `project/` outside the walk. Design declares the same name and depends on it more heavily, since base plus target-owned override is the whole of its channel and an override named exactly like the shipped `base.css` still has to survive a sync. The flat root still keeps the name inference, so two mechanisms answer the ownership question. Location wins before a name lookup runs because a name-only `locateSource` reads a relocated toolkit file as project-authored with no command able to tell the two apart: five toolkit standards moved into a subfolder produced 17 such files across three targets. The name inference stays as a floor under new files rather than being replaced. Measured at `5da3214d` on 2026-08-25.
- A comparably-shaped external project reached the same mechanism for its own install-and-update path without sharing any code: hash what shipped, compare it three ways against what the project holds and what it last recorded, and skip whatever the project edited. Its version is 779 lines against `src/sync/`'s 5,787, and the convergence matters more than the gap, since two projects reasoning independently to one answer is stronger evidence for the mechanism than either project's own reasoning. Measured at `d5f519ee` on 2026-08-26.
- `installPattern` is the fourth optional field and the first one a domain needed for a reason other than its policy. The walk listed `**/*.md` unconditionally, which is every domain that ships prose, and design ships a stylesheet. It defaults to `DEFAULT_INSTALL_PATTERN`, so no existing adapter changed, and design sets `**/*.css`.
- Which mechanism decided is visible in the report for an adapter declaring `projectSubdir`, which today is design alone. `misplacedOrphan` gives the name-inferred orphan a notice naming the path under `projectSubdir` it would take, and the location-orphaned file keeps the generic line. The notice queues no change, since moving a file rewrites a path the project's own content may cite, so the sync reports the placement and leaves the decision with whoever owns the citations.
- The notice offers that path on a condition rather than asserting the project wrote the file. No source name matching is what a project-authored file looks like and equally what a file the toolkit shipped and later renamed looks like, and the stamp cannot split them: `recordStamp` skips a file whose source is gone and `writeStamp` replaces the domain's whole `files` map, so a renamed file's entry survives exactly one sync past the rename and an unstamped target has none to read. Only the operator knows which they are looking at, so the line asks rather than tells.
- Gov answers that question by location instead, through `ownsInstalledRoot`. The toolkit owns a target's `.claude/rules/canon/` outright and a project keeps its own rules under `.claude/rules/project/`, which the walk never reaches, so a walked file with no source is a rule the toolkit retired or renamed. `planSync` classifies it `retired` and queues its delete, edited or not and whatever the stamp holds. Reporting it as orphaned and skipping it would leave a retired rule loaded in every target that installed it. A read of the six registered targets holding a `canon/` rules folder found no file there the toolkit does not ship, measured at `4f7cde48` on 2026-09-25.
- Two alternatives lost. Deleting only a file whose content still matched its stamped hash kept an edited rule alive forever and deleted nothing in a target installed before stamping, and the stamp drops a retired file's entry one sync after the retire regardless. A shipped ledger of retired rule names would have to be kept by hand on every retire and still say nothing about a rename nobody recorded.
- The stamp records the newest canon release that wrote each domain, and `planSync` holds every sourceless file as `orphaned`, naming both releases, when that release is newer than the running one. A binary older than the release that installed a rule cannot tell it from one the toolkit retired, so without the guard a downgrade deletes every rule added in between. `putDomain` keeps the higher of the recorded and running releases rather than overwriting, since an older binary lowering the mark would let its next run delete what the guard held on the first.
- A rename or renumber installs the rule under its new name only when `governance/renames.toml` declares it. `renamed` is the fourth sourceless state and the only one that installs: after the newer-install guard, `planSync` asks the optional `locateSuccessor` member, and a hit queues a copy of the successor's source and a delete of the old file. The copy is skipped when the target already holds the successor or an earlier entry in the same walk queued it, so two predecessors of one rule copy once. A miss keeps `retired`, which is where an undeclared rename still lands.
- The ledger won over three inferences, each of which fails on this tree. Matching on the slug after the number collides on three pairs of record-folder rules today. Git rename detection at sync time needs toolkit history a registry install lacks. Content similarity breaks on a regroup that rewrites bodies. The retirement ledger rejected above had to be kept on every retire, while this one covers only renames, the one fact no packaged file otherwise records. It is transitive and never pruned, so a target several releases behind still reaches the current name, and `src/gov/renames.test.ts` fails on a key naming a live rule, a chain ending on no source, or a cycle.
- The gov adapter reads no chain for a rename, since holding the predecessor is the evidence of entitlement, and that covers a rule layered on with `--add`. The successor lands in the source's band folder unless the target already holds it in another one. The toolkit's source is installed rather than the old file's content, so a local edit is dropped the way `retired` drops one, and the notice says so. The missing-rules readers count a held rule's successor as held, so `--check` names a mid-rename file once, as `renamed`.
- `canon sync --check` skips every orphaned entry in `src/commands/sync.ts` and lists every `retired` and `renamed` one, and `hasDrift` counts both, since a sync closes each mechanically. A target's CI goes red on `--exit-code` the day a release retires a rule it holds, and one sync clears it.
- The name reserves `project` across the toolkit's own `governance/rules/` source tree too, not only across a target's installed copy. `src/gov/adapter.test.ts` asserts its tree holds no `project/` category, which is what would fail first if a later toolkit category collided with the reserved name.
- The sync commit stages the paths the syncs actually changed rather than `git add -A`. The workflow already reads those paths to classify each domain, so the commit matches its own message. `check_clean_tree` stays regardless, since it is what makes any staging choice survivable.

## canon sync

`canon sync [target]` runs every installed domain sync in sequence (governance, claude), then a git workflow step that detects which domains changed and previews the commit and pull request body before prompting. Neither standards nor snippets sits in that sequence, since neither installs into a target for a sync to reconcile. Committing creates `chore/canon-sync-YYYYMMDD-HHMM` when the run is on `main` or `master` and stays on the current branch otherwise. The pull request body lists up to three changed filenames per domain, then a count for the rest.

Claude sync runs under `CANON_NON_INTERACTIVE=1` so the embedded call does not prompt. The one other domain sync, governance, inherits stdin and prompts for its own changes, and the combined pull request preview is the confirmation gate for the workflow alone. `canon claude sync` writes only `.gitignore`, so the changed-file tracking watches that path and a gitignore-only change still reports under a `claude/` domain line. Seed audits stay a manual step through the `seed-sync` skill, which `canon sync` points at when `.claude/` is present.

Governance is the one domain whose sync condition differs from its detection condition. It reports as absent without `.claude/rules/`, yet still syncs when only the retired `.claude/GOV.md` remains, so that the sync can delete it.

The workflow is skipped when the target is not a git root, and the pull request path is hidden when `gh` is missing while committing still works. It stops with a warning when the timestamped branch already exists locally or on the remote, and two runs inside one minute collide by design.
