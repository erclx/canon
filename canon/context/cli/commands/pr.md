# Pull request verbs

`canon pr head` and `canon pr checks` both resolve the branch tip through `git ls-remote` and key what they report on that sha, rather than through `gh pr view --json headRefOid`, which reads a field on the pull request object that trails the branch ref by up to a minute after a push and says nothing about the trail. The remote rather than the remote-tracking ref, since a tracking ref is only as current as the last fetch and the push worth catching is the one the process never saw. It costs roughly half a second against 0.001s for the local read, sampled at 0.41s, 0.55s, and 0.67s across two days, on callers that already spend a `gh` round trip on the same line. `docs/agents/pr-reads.md` carries why that spend is right in the orchestrator poll and wrong in `canon targets pulls`, which is a question about what each reading decides rather than about what it costs.

`canon pr review-state` is the third verb under `pr` that exists because a GitHub field answers a different question than the one a caller is asking. `commit.oid` and `submittedAt` on a review are stamped at submission, so a push landing between a pass's read and its post moves both onto a commit that pass never opened. `review-pr` writes the commit it read and the instant it read it as an HTML comment on the last line of every body it posts, and `src/pr/review-scope.ts` parses that marker off the newest pass in the review family, falling back to the two stamps for a pass posted before the mechanism shipped. `source` on the record names which answered, so a caller can tell a read-time reading from a stamped one. It is the only parser of the format, which is what stops the shipped skill body and the shipped `poll.sh` from carrying a copy each on two release cadences.

`src/pr/evidence.ts` answers a different question than the three verbs above: which changed images `git-pr` and `git-followup` should compare in one pull request comment, grouped by the state and the stem the path's `evidence/` segment carries, and whether each existed at the merge base. `canon pr evidence` reads the base and the changed set from the local checkout's own git history rather than fetching them for a named pull request over the API, which is correct only when the caller runs it from the branch the named pull request describes. Both call sites always do, since neither ever passes a number for another branch. The comment carries a trailing `<!-- pr-evidence: head=<sha> -->` marker parsed back off `gh pr view --json comments`, the same shape `review-state` reads for its own marker, so a later call edits the same comment in place instead of posting a second one. `isEvidencePath` requires both an `evidence/` segment and an image extension, since this repository's own evidence tree holds eight `.md` files, two `.sh` scripts, a `.tsv`, a `.json`, and an `.html` file against a single `.png`, and a path test on the segment alone rendered every one of those as a broken `![]()` embed. `## Evidence` is the sixth heading `role-orchestrator`'s poll classifies, excluded from its unmatched set rather than folded into the reply family, since the comment answers no review and posting one should never send the poll back for a re-review.

`canon pr preview` is the one verb under `pr` that writes to the world, since it dispatches a deploy. `src/pr/preview.ts` refuses a workflow in which any `pages deploy` line lacks `--branch=${{ github.ref_name }}`, reading with YAML comment lines dropped, because Cloudflare Pages publishes an unfenced deploy to production and a fence named only in a comment would otherwise pass for one. It reads the preview alias off a `canon-preview-alias:` line in the finished run's log rather than computing it from the branch name, since Cloudflare flattens and may truncate a branch into its alias. `gh workflow run` returns no run id, so the run is the one id absent from a listing taken before the dispatch, which keeps the match off the local clock. The address reaches the pull request as the first line of the evidence body through `canon pr evidence --preview`, and a later render without the flag carries the address forward off the marked comment, so `git-followup`'s re-render after a push keeps the link. An unreadable comment thread refuses as `gh-failed` rather than rendering blind, since a body built without it knows neither the comment to edit nor the address to carry.

`canon pr local` finds the branch's dev server by the working directory of each listening process rather than by deriving a port, since a port helper needs a per-stack base the toolkit cannot know and misses a server started by hand. `src/pr/local.ts` keeps a listener whose cwd sits inside the worktree toplevel, subfolders included, and excludes everything under `.claude/worktrees/` so the main checkout never reports a linked worktree's server. The probe counts only a port serving `text/html` at `/`, because a run from the main checkout here found a Playwright test server answering a bare 404 in the same tree. The link lands as a `**Local preview:**` line under the hosted one through `canon pr evidence --local`, which does not flip `no-evidence` by itself, so a docs-only branch with a server up posts no link-only comment. A seeded `pull_request: closed` workflow removes it with `--remove`, the one path where the verb edits the comment itself, since that caller has no session to post a body. The workflow covers close alone, so a link whose server stopped mid-review stays up until then. Measured at `18c5aa17` on 2026-09-25.

The machine runner reads listeners from `/proc` wherever `/proc/net/tcp` exists and turns to lsof only without it, or when both tables fail to read. lsof 4.95, which Ubuntu 24.04 ships, drops every process whose kernel-truncated name holds an unmatched `(`, and Next's `next-server (vX.Y.Z)` title truncates to `next-server (v1`, so an lsof-first order answered `no-server` for every Next dev server on such a machine. Falling back to `/proc` only when lsof found nothing inside the worktree was the alternative, and it keeps two readers that disagree in exactly that case. The price is a `/proc` scan of about 341 ms against 49 ms for lsof over 3791 fds. Measured at `f6a2d68b` on 2026-09-25.

`src/pr/checks.ts` imports `rollup` from `src/targets/pulls.ts` rather than writing a second collapse. The import crosses from `src/pr/` into `src/targets/`, which reads backwards, and the alternative was a third module both import from, at the cost of moving a function two callers already share correctly. What the boundary carries instead is a vocabulary conversion: `rollup` reads the GraphQL enum the pull request listing returns and the REST check-run row spells its statuses lowercase, so `adapt` raises each row into upper case and maps a null conclusion onto an absent one before the collapse runs.

Keying a query on a sha is necessary and not sufficient, which is the case that shaped the verb rather than a note beside it. `repos/{owner}/{repo}/commits/<sha>/check-runs` answered with `total_count` 2 and an empty row list during a measured window, so a reader that finds no run for the tip and reports `passing` reproduces the false green behind a better query. Both empty shapes report `pending`, and `matched` and `foreign` on the record are what let a caller separate a tip with no run yet from one whose listing describes another commit. The foreign test runs ahead of the collapse, so a mixed listing never gets a verdict off the half that happens to match.

Truncation is the third shape. The endpoint pages at 30 by default, so a commit carrying more check runs than that comes back short with `total_count` naming the whole, and collapsing the page in hand reports `passing` off a set a failing run can sit outside of, which is the same false green through a different door. `runChecks` asks for 100, the endpoint's maximum, and `collapseChecks` reads `reported` above the rows it holds as `pending` whatever they say. The two compose rather than either standing alone, since the ceiling only moves the boundary and the guard is what makes crossing it report unread. Measured at `e6ac473f` on 2026-09-02.

A conflicted branch is the empty listing that never fills, since no merge ref exists for a `pull_request` workflow to run on. The record carries `conflicted` beside `state` rather than a fourth `state` value, because the rollup and `canon targets pulls` branch on the three-value `ChecksState` and a fourth would fail open in any caller without a default arm. `withMergeState` sets it only on `DIRTY` with `matched` 0, so a conflict arising after runs completed keeps their verdict.

A re-triggered gate is the fourth shape: a check re-run after a body edit leaves both the stale failed run and the fresh passing run attached to the same head, and a naive fold can count the failed one toward the state. `newestPerCheck` groups the matched set by name and keeps the run carrying the highest `id` per group. One carrying no name keys on its own position instead, so it never joins another nameless run's group. `collapsed` on the record counts what that fold discards, so a caller reading it against `matched` sees the dedupe rather than guessing at it from a state that disagrees with `gh pr checks`. Measured at `50c523f5` on 2026-09-02.
