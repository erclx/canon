# Pull request verbs

`canon pr head` and `canon pr checks` both resolve the branch tip through `git ls-remote` and key what they report on that sha, rather than through `gh pr view --json headRefOid`, which reads a field on the pull request object that trails the branch ref by up to a minute after a push and says nothing about the trail. The remote rather than the remote-tracking ref, since a tracking ref is only as current as the last fetch and the push worth catching is the one the process never saw. It costs roughly half a second against 0.001s for the local read, sampled at 0.41s, 0.55s, and 0.67s across two days, on callers that already spend a `gh` round trip on the same line. `docs/agents/pr-reads.md` carries why that spend is right in the orchestrator poll and wrong in `canon targets pulls`, which is a question about what each reading decides rather than about what it costs.

`canon pr review-state` is the third verb under `pr` that exists because a GitHub field answers a different question than the one a caller is asking. `commit.oid` and `submittedAt` on a review are stamped at submission, so a push landing between a pass's read and its post moves both onto a commit that pass never opened. `review-pr` writes the commit it read and the instant it read it as an HTML comment on the last line of every body it posts, and `src/pr/review-scope.ts` parses that marker off the newest pass in the review family, falling back to the two stamps for a pass posted before the mechanism shipped. `source` on the record names which answered, so a caller can tell a read-time reading from a stamped one. It is the only parser of the format, which is what stops the shipped skill body and the shipped `poll.ts` from carrying a copy each on two release cadences.

Every read under `pr` runs on REST, because a cloud session's GitHub proxy refuses GraphQL and every `gh pr view` and `gh repo view` runs on it. `src/pr/rest.ts` is the one boundary where the pulls, reviews, and issue-comments payloads meet the field names `review-scope.ts`, `evidence.ts`, and `withMergeState` were written against. Keeping GraphQL locally and falling back to REST after a 403 was the alternative, and it doubles the test surface for one field. That field is `mergeStateStatus`, which REST lacks. `mergeable_state` holds the same values in lower case, so `mergeStateOf` raises it, and `unknown` stays `UNKNOWN` while GitHub computes it lazily, which `withMergeState` already reads as not conflicted. A call with no number lists `pulls?head={owner}:<branch>&state=open` and refuses `ambiguous-pull` on two rows rather than taking the first, since two open pull requests on one head against different bases are both real. The reviews and comments reads pass `--paginate` and emit one `@json` line per row, because a filter reshaping each row makes `--paginate` emit one value per page, and a `last` inside the filter would answer for each page rather than the thread. A refused page refuses the verb as `gh-failed` rather than reading as no reviews. `src/commands/pr.test.ts` drives each verb through a stub `gh` that 403s any `pr`, `repo view`, or `graphql` call, so a reintroduced one fails the suite.

`src/pr/evidence.ts` answers a different question than the three verbs above: which changed images `git-pr` and `git-followup` should compare in one pull request comment, grouped by the state and the stem the path's `evidence/` segment carries, and whether each existed at the merge base. `canon pr evidence` reads the changed set, each path's added-or-modified status, and the merge base for the named pull request over the API, through the paginated files endpoint and the compare endpoint, rather than from the local checkout. The checkout read it replaced rendered an empty comparison, and with `--preview` reported `ok` over it, when an orchestrator ran it from the main worktree against a branch built elsewhere, and `review-ui` and the orchestrator both read the record by number from outside the branch. Refusing when the checkout head differed from `headRefOid` was the alternative, and those two callers would have hit it. The trade is that uncommitted or unpushed evidence goes unseen, which the head-pinned image links could not show anyway. A render with no cases over a marked comment that carries some refuses `would-empty` and prints no body, since an emptied render cannot tell a removal from a short read. The comment carries a trailing `<!-- pr-evidence: head=<sha> -->` marker parsed back off the issue comments endpoint, the same shape `review-state` reads for its own marker, so a later call edits the same comment in place instead of posting a second one. The record reports what that marked comment already holds as `preview`, `local`, and `checklist`, each present only when the comment carries it, on `ok` and `no-evidence` alike, read through the same finders the carry-forward uses so no skill parses the comment a second time. The thread is therefore read ahead of the `no-evidence` return, and an unread thread refuses as `gh-failed` there too rather than reporting the fields absent. A checklist alone renders `ok` with a marked body, reversing the earlier rule that a checklist did not decide `no-evidence`. That rule kept a docs-only branch from posting a comment, but a branch with a checklist changed a rendered surface, and an unmarked standalone post left `review-ui` and the owed check unable to find it. `git-pr` keeps the raw post only as the fallback for a git refusal, which stays unmarked and reports no `checklist`. `isEvidencePath` requires both an `evidence/` segment and an image extension, since this repository's own evidence tree holds eight `.md` files, two `.sh` scripts, a `.tsv`, a `.json`, and an `.html` file against a single `.png`, and a path test on the segment alone rendered every one of those as a broken `![]()` embed. `## Evidence` is the sixth heading `role-orchestrator`'s poll classifies, excluded from its unmatched set rather than folded into the reply family, since the comment answers no review and posting one should never send the poll back for a re-review.

`canon pr evidence --check` reports which post-pull-request steps of the ship chain never landed, as `owed` drawn from `evidence` and `preview`, through `readOwed` over the same API changed set and thread the render reads. It reads the pull request rather than a session's account of what it ran, since a session that stops after opening the pull request is exactly the one whose account is missing, and a branch it leaves reads the same as one that needed neither step. Four surfaces read it: `role-orchestrator`'s draft lift, the `git-pr` run on every pull request, the closing read of `git-ship`, and step 5 of `git-followup`. The draft lift is the one act reading it by number from outside the branch, which matters because a session that skipped the chain would skip a check inside it too. A new verb was the alternative and would have restated both reads. The thread cannot tell a skipped preview from a failed deploy, so both read as owed and the cause stays with the worker. The deploy workflow is read from the checkout, so a pull request changing its own deploy reads against trunk's. A checklist-only branch posts a marked comment, so it reads as owing a preview once that comment exists.

`canon pr preview` is the one verb under `pr` that writes to the world, since it dispatches a deploy. `src/pr/preview.ts` refuses a workflow in which any `pages deploy` line lacks `--branch=${{ github.ref_name }}`, reading with YAML comment lines dropped, because Cloudflare Pages publishes an unfenced deploy to production and a fence named only in a comment would otherwise pass for one. It reads the preview alias off a `canon-preview-alias:` line in the finished run's log rather than computing it from the branch name, since Cloudflare flattens and may truncate a branch into its alias. `gh workflow run` returns no run id, so the run is the one id absent from a listing taken before the dispatch, which keeps the match off the local clock. The address reaches the pull request on the address line under the evidence body's `## Evidence` heading through `canon pr evidence --preview`, and a later render without the flag carries the address forward off the marked comment, so `git-followup`'s re-render after a push keeps the link. An unreadable comment thread refuses as `gh-failed` rather than rendering blind, since a body built without it knows neither the comment to edit nor the address to carry.

`canon pr preview` refuses `unserved`, mint and `--check` alike, when the deploy workflow's own `on.push.paths` or `paths-ignore` filter matches no path the pull request changed. The evidence comment on #2221, a canvas-only branch, linked a landing-page deploy because `git-pr` minted whenever a checklist or evidence posted, and the only deploy run on that branch was a `workflow_dispatch` run, which GitHub starts without consulting the push filter. The filter is the source rather than a second path list in canon config, since it already decides when production deploys and a second list would drift from it. `readServedPaths` parses it with `Bun.YAML` and `servesChange` matches each changed path with `Bun.Glob`, applying `!` patterns in order as GitHub does. A workflow with neither filter, with no push trigger, or that fails to parse serves every change, because a wrong `unserved` stops all four readers of `readOwed` asking for a preview and lets the draft lift clear a branch whose site never deployed. The changed set comes off `listPullFiles`, the same REST read the evidence render takes, with removed paths counted here though the render skips them, since GitHub's own push filter counts a deletion. `--check` on `canon pr evidence` stops owing `preview` on such a branch, and a render drops a carried hosted address the change does not reach while keeping an explicit `--preview`. This repository's `deploy-site.yml` excludes `assets/evidence/**` from its `assets/**` entry, since the page reads nothing there and every branch carrying screenshots otherwise read as served. Measured at `a4f823022` on 2026-10-04. A workflow fixture whose alias step reads `run: echo "canon-preview-alias: $URL"` unquoted is not valid YAML, since `: ` inside a plain scalar opens a mapping, so `Bun.YAML.parse` throws and the reader serves every change. A test exercising a filter writes that step as a block scalar.

`canon pr preview --check` answers whether the preview a reviewer is about to drive was built from the branch tip, because `review-ui` posted `## UI review closed` on `#2051` against a build of an earlier head with nothing comparing the two. The newest successful `workflow_dispatch` run is the source, since the alias serves the newest successful deployment per branch and names no sha, so the run listing is the only record of the built head. `readPreviewHead` orders runs by `createdAt` rather than list position and reads a run still going at the tip as `building` rather than `stale`. The `--event workflow_dispatch` filter is load-bearing, because the deploy workflow's `pull_request: closed` cleanup run concludes `success` with its deploy skipped and would read as a fresh build. The tip comes from `resolveTip` against the remote, not `headRefOid`, which lags a push. Enforcing it in the ship chain by re-minting on push was the alternative, and it is a second surface that stays a follow-up. Reading `built` off the alias URL was rejected, as the alias carries no sha. The gap that stays is the local rung and a launch-named address, which have no run to read and stay unverified, and a hand-run `wrangler` deploy outside the workflow, which the run listing never sees.

`canon pr local` finds the branch's dev server by the working directory of each listening process rather than by deriving a port, since a port helper needs a per-stack base the toolkit cannot know and misses a server started by hand. `src/pr/local.ts` keeps a listener whose cwd sits inside the worktree toplevel, subfolders included, and excludes everything under `.claude/worktrees/` so the main checkout never reports a linked worktree's server. The probe counts only a port serving `text/html` at `/`, because a run from the main checkout here found a Playwright test server answering a bare 404 in the same tree. The link lands as a `**Local preview:**` segment after any hosted one on the address line through `canon pr evidence --local`, which does not flip `no-evidence` by itself, though a checklist does, so a docs-only branch with a server up posts no link-only comment. A seeded `pull_request: closed` workflow drops the whole address line with `--remove`, the one path where the verb edits the comment itself, since that caller has no session to post a body. It drops the hosted segment too and leaves no note, because the deploy workflow's cleanup job deletes the branch's preview deployments on the same close and a tombstone sentence outlived the links on #2212. The reader that finds the line scans the region above the commit line, checklist, or comparison for each prefix wherever it sits, so a comment in the older layout, opening on the addresses rather than the heading, reads the same. The workflow covers close alone, so a link whose server stopped mid-review stays up until then. Measured at `18c5aa17` on 2026-09-25.

The machine runner reads listeners from `/proc` wherever `/proc/net/tcp` exists and turns to lsof only without it, or when both tables fail to read. lsof 4.95, which Ubuntu 24.04 ships, drops every process whose kernel-truncated name holds an unmatched `(`, and Next's `next-server (vX.Y.Z)` title truncates to `next-server (v1`, so an lsof-first order answered `no-server` for every Next dev server on such a machine. Falling back to `/proc` only when lsof found nothing inside the worktree was the alternative, and it keeps two readers that disagree in exactly that case. The price is a `/proc` scan of about 341 ms against 49 ms for lsof over 3791 fds. Measured at `f6a2d68b` on 2026-09-25.

`canon pr frames` is the second verb under `pr` that writes to the world, and it writes one ref, `refs/heads/canon-frames`, through the git data API so the reviewer that calls it still checks nothing out. It exists because `review-ui` could only describe a frame in words, since nothing outside the merge path held an image a review comment could embed. The operator settled the store on 2026-10-02. A local clone of the branch lost because it needs a worktree the reviewer may not enter. Dropping frames at close lost because it breaks a recent review's images the moment its pull request merges. The branch never merges and holds only frames the worker's evidence lacks, which `review-ui` decides by matching a box against the `states` that `canon pr evidence` now reports, a judgment the verb never makes. `src/pr/frames.ts` keeps the logic behind an injected `FramesApi`, so a test drives the git object model in memory. Its cost is history. A plain delete would keep every image reachable, so `--drop` and `--prune` write a root commit and force-move the ref. That rewrite is why the link names the branch path rather than a commit, since a commit-pinned link to any other pull request's frame went unreachable at every drop and resolved only until GitHub collected it. A path link mutates when its file does, so the path carries a pass segment, the compact UTC instant `review-ui` records at its first step, and a second pass at one head and box writes a new file rather than changing an image an earlier comment shows. Refusing the overwrite lost, since a preview minted again at one head needs a second pass there. `--prune 30` runs daily from `pr-frames-cleanup.yml` rather than on `pull_request: closed`, with the expiry selection in the verb where a test reaches it, and a target project carries no such workflow yet.

`src/pr/checks.ts` imports `rollup` from `src/targets/pulls.ts` rather than writing a second collapse. The import crosses from `src/pr/` into `src/targets/`, which reads backwards, and the alternative was a third module both import from, at the cost of moving a function two callers already share correctly. What the boundary carries instead is a vocabulary conversion: `rollup` reads the GraphQL enum the pull request listing returns and the REST check-run row spells its statuses lowercase, so `adapt` raises each row into upper case and maps a null conclusion onto an absent one before the collapse runs.

Keying a query on a sha is necessary and not sufficient, which is the case that shaped the verb rather than a note beside it. `repos/{owner}/{repo}/commits/<sha>/check-runs` answered with `total_count` 2 and an empty row list during a measured window, so a reader that finds no run for the tip and reports `passing` reproduces the false green behind a better query. Both empty shapes report `pending`, and `matched` and `foreign` on the record are what let a caller separate a tip with no run yet from one whose listing describes another commit. The foreign test runs ahead of the collapse, so a mixed listing never gets a verdict off the half that happens to match.

Truncation is the third shape. The endpoint pages at 30 by default, so a commit carrying more check runs than that comes back short with `total_count` naming the whole, and collapsing the page in hand reports `passing` off a set a failing run can sit outside of, which is the same false green through a different door. `runChecks` asks for 100, the endpoint's maximum, and `collapseChecks` reads `reported` above the rows it holds as `pending` whatever they say. The two compose rather than either standing alone, since the ceiling only moves the boundary and the guard is what makes crossing it report unread. Measured at `e6ac473f` on 2026-09-02.

A conflicted branch is the empty listing that never fills, since no merge ref exists for a `pull_request` workflow to run on. The record carries `conflicted` beside `state` rather than a fourth `state` value, because the rollup and `canon targets pulls` branch on the three-value `ChecksState` and a fourth would fail open in any caller without a default arm. `withMergeState` sets it only on `DIRTY` with `matched` 0, so a conflict arising after runs completed keeps their verdict.

A re-triggered gate is the fourth shape: a check re-run after a body edit leaves both the stale failed run and the fresh passing run attached to the same head, and a naive fold can count the failed one toward the state. `newestPerCheck` groups the matched set by name and keeps the run carrying the highest `id` per group. One carrying no name keys on its own position instead, so it never joins another nameless run's group. `collapsed` on the record counts what that fold discards, so a caller reading it against `matched` sees the dedupe rather than guessing at it from a state that disagrees with `gh pr checks`. Measured at `50c523f5` on 2026-09-02.
