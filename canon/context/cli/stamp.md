# Install stamp

The stamp is the record a sync reads to separate a file the toolkit moved from a file the project edited. `canon/context/cli/sync.md` carries the engine that writes and reads it.

## The stamp

- A content hash answers whether a file changed. Only a record written at install time answers who changed it, and those two need opposite actions. That is the whole reason `canon/config/config.json` exists rather than recomputing against the source, which is what `planSync` already did.
- The stamp's path list is a second input to the walk, not a lookup keyed by the current path. A relocated file is never walked, so a lookup would never consult its entry and the stamp would buy nothing a recomputed hash does not. Folding stamped paths into the walk is what makes a move visible.
- `orphaned` and `stranded` are separate states because they need opposite treatment. A project-authored rule is orphaned and never converges, so counting it as drift left `--exit-code` failing forever with no remedy. A stamped file at a root the toolkit abandoned is stranded, which is a relocation waiting on a decision. `retired` is the third sourceless state and the only one a sync acts on: it needs no stamp at all, since the walked root being the toolkit's is what decides it.
- The stamp writes after the copies land, so a partial apply that throws leaves the previous stamp rather than a claim the target does not meet. A stamp that lies is worse than no stamp, because the next report calls updated files stale.
- `canon/config/` takes a loose config file the toolkit owns, plus `baseline.json`, the one generated file that outgrew its own folder. Installed content a project reads and edits keeps its own folder, which is `.claude/rules/`. Ownership is not the test, and being a bare file in the shared root is, which the config and the baseline both satisfy.
- `putDomain` is the one place the machine-level target index is kept, because every install and sync that stamps a target passes through it and no install command has to remember. The index sits at `$XDG_STATE_HOME/canon/targets.json`, resolved by `stateDir` in `src/targets/registry.ts` the same three ways `sandboxTree` resolves the sandbox. Its `recordTarget` outcome is dropped deliberately: the stamp written a line above is the authoritative record of that install, the index is a cache over every such stamp, and a state folder nobody can write is not a reason to fail a sync whose files already landed.
- The index is a record of installs as they happen rather than a search for them, since a filesystem walk answers about the paths someone thought to name. A hand census run twice against one folder got both wrong: it reported six consuming projects across eight folders, where two had never been targets, one was a second clone of a target already counted, and the clone a repair actually ran in sat outside the folder entirely. The sweep stays as a fallback for installs that predate the index and carries its bound with the answer, naming the roots walked, the depth, the folders it stopped at, and the roots it could not read. Grouping by origin makes a target held in two clones count once, and a linked worktree carries a copy of its own target's stamp. Nothing removes a row, so a deleted project inflates the count until a read refuses its path. Measured at `427213fc` on 2026-08-30, against eight targets on this machine.
- `backfillTarget`, beside `recordTarget` in `src/targets/registry.ts`, is the index's second writer. `canon targets list --sweep <root> --record` calls it once per checkout a sweep finds, dated by that checkout's own `readStamp` rather than by the moment the backfill ran, for the population a target predating the index left unrecorded.
- `stateDir` checks `CANON_STATE_DIR` ahead of `XDG_STATE_HOME`, an override that exists so a test never writes into the home directory of whoever runs it. A caller spawning `gov install` or `gov sync` as a real process rather than calling it in-process inherits the real `HOME` unless it sets that override itself, which writes a row into this machine's real index for a fixture directory about to be deleted. `sandboxTree` in `src/commands/sandbox.ts` resolves the same three ways under `CANON_SANDBOX_DIR` and lands one folder below `stateDir`'s own result, so a caller redirecting one without the other still reaches the real machine through `canon sandbox`. `canon/context/development/verification.md` covers the process tier's handling of both.
- Nothing walking a filesystem for targets may stop at the first stamped folder it finds, since a stamped folder can hold others. `private/career` on this machine carries its own stamp and contains eight further repositories, each stamped in turn, so a walk that stopped at the first reports the outer target and hides every one nested below it. A linked worktree under `.claude/worktrees/` carries a copy of its own target's stamp as well, which is why the walk skips `.claude` outright rather than reading five worktrees of one target as five targets. Measured 2026-08-30.

## What the stamp covers

- A missing or corrupt stamp degrades to the unattributed report rather than failing, which is the only path an unstamped target has.
- Tooling is a stamp domain without being a scanned one. `src/tooling/` never calls `planSync`, so it records the stack chain it resolved instead of file hashes, and `SCANNED_DOMAINS` in `src/sync/check.ts` is the narrower list the adapter, source-path, and install-marker lookups are keyed on, and the closing unstamped line reads it too. Three stamp domains stand against two scanned ones, since design joined both lists doing per-file work the way governance does.
- `OPT_IN_DOMAINS` is what the unstamped line reads on top of `SCANNED_DOMAINS`, and `uncoveredDomains` composes the two. A target absent governance has yet to install what every managed project carries, so naming it is the only place that shows up. A target absent design chose that, and naming it would route every existing target to `canon design sync`, which warns `No design surface found` and exits 0.
- Governance is the one domain in both lists. `canon gov install` calls `writeChainStamp` beside `recordStamp`, so a governance record carries file hashes for what a sync would refresh and a chain for what the stack it was given entitles it to. `putDomain` merges the two independently: a write naming only `files` or only `chain` keeps the other half of that domain's previous record rather than dropping it, which is what lets `writeStamp` and `writeChainStamp` each own one half of the same domain across two calls that never run together.
- Adding a domain means deciding which of the two lists it joins. Retiring one means editing both, and `STAMP_DOMAINS` is the edit that reaches a target's existing file.
- `isStamp` validates only the domain records whose key names a current `StampDomain` and ignores the rest, rather than rejecting the whole file on an unknown key. Rejecting it makes `readStamp` return undefined, which `putDomain` then reads as an unstamped target and rewrites from nothing, so retiring one domain from the union would silently discard every other domain's hashes on the next sync. `sortDomains` drops the retired key at that write, which retires it with no migration. The `standards` and `snippets` keys a target holds from their closed install channels are the case this covers.
- The chain's shape follows what its reader needs, not one fixed contract. Tooling stores the full ordered ancestor chain, nearest first, because a stack extends another and a `--skip` run installs fewer layers than the leaf's chain reproduces, so the report loads the recorded stacks directly rather than re-resolving. Governance stores only the leaf `canon gov install` was given, since `resolveRules` walks that stack's own `extends` ancestors internally and a reader asking it again needs nothing more.
- `chain` is optional on `DomainStamp`, which keeps a stamp written before tooling joined the domains parsing rather than reading as corrupt and discarding the three records it does carry.
- A workspace root records no chain. One chain written there is a guess at what its packages hold, and the report saying unmeasured is the true answer. The detection reads `workspaces` in `package.json` and `pnpm-workspace.yaml`, and lives in `src/tooling/stamp.ts` so `src/sync/` never learns what a workspace is.
- Only a whole-stack install records. A flag-scoped `canon tooling inject --gitignore` installs one category, and a chain recorded from it would send the report scanning for configs and deps the caller never asked for. The `claude` stack is excluded at that call site rather than in `prepare`, which is what keeps `canon claude` able to drive injection.
- Naming the domains a target has not stamped, rather than the domains the toolkit could stamp, is what tells an uncovered domain from a clean one.
- The anchor sits per domain rather than at the top of the stamp. Domains sync independently, so one shared revision lets one domain's sync advance the commit another measures its upstream range from, dropping that domain's changes out of the read. Per-file attribution never sees it, because `attribute` compares hashes and never reads the anchor, which is what makes it fail quietly.
- `covers` is derived from the domains actually recorded, never from the constant list of domains the engine can stamp. A compile-time constant claimed coverage of domains a target had never stamped, which is the ambiguity the field exists to remove.
- `readStamp` falls back to the retired `.claude/aitk.json` when `.claude/canon/config.json` is absent, read only. The path moved with no migration, so a target stamped before the move reads as unstamped without the fallback, which zeroes every read keyed on the stamp. `isLegacyStamped` answers whether that fallback fired, so `canon sync --check` can report the retired path rather than silently reading through it forever.
- `src/targets/sweep.ts` and `src/targets/resolve.ts` call the same `isLegacyStamped` per checkout and carry it as `legacyPaths`, a subset of a group's `paths`. `canon sync --check` stays a per-target report with no group to collapse into a boolean.
- `stampPaths` reads `canon/config/config.json` ahead of `.claude/canon/config.json`. `src/surface-root.ts` carries a second root list rather than reusing `RECORD_ROOTS`, since a stamp is committed rather than gitignored and a shared list would put a session record folder under a root a tracked file also resolves against.
- The fixed path resolves through `resolveExisting` in `src/legacy-path.ts`, which `stamp.ts`, `src/audits/baseline.ts`, and `src/labels/map.ts` all call, so a later move edits one function rather than three copies of the same reasoning. `sweep.ts`'s `isStamped` still lists its own paths, since it answers a different question, whether any spelling exists, rather than which one wins.
