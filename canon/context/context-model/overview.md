# Context model

## Overview

This is the cross-domain design doc for how a project splits agent context across loading tiers, and the operating manual for `canon/context/` itself. It governs every entry in the folder rather than describing one domain.

It stays one file past the length checkpoint because `CLAUDE.md` cites its path for the test that sorts a fact between tiers and roots, and every section answers the same question of where a fact belongs.

### Three loading tiers

Target projects scale by splitting context across three tiers.

| Tier             | Where                                                 | Holds                                                     |
| ---------------- | ----------------------------------------------------- | --------------------------------------------------------- |
| Always loaded    | root `CLAUDE.md`, `canon/REQUIREMENTS.md`             | cross-cutting behavior and product scope                  |
| Path-scoped lazy | `.claude/rules/<scope>.md` with `paths:` frontmatter  | do and don't rules for a file scope, loaded on glob match |
| On-demand lookup | `canon/context/<domain>.md`, `.claude/wiki/<page>.md` | per-domain narrative and reference, indexed for discovery |

`canon/context/` exists for discoverability rather than load cost. A nested `CLAUDE.md` loads lazily when its subtree is read, so it is already cheap, and what it lacks is any signal that it exists. The `index.md` catalog lists every entry up front, so a session picks the one it needs before touching the domain.

## Layout

Flat by default, one `.md` per domain. Use a folder (`canon/context/<domain>/<sub-area>.md`) only when a domain has 3+ sub-areas that do not fit in one file. A folder may also group the whole entries of several small domains sharing one kind, which `claude/skills/context-fold/references/context.md` states under `## Length`.

- `canon/context/index.md` is regenerated by `canon indexes regen` from each entry's `title` and `description` frontmatter. Do not hand-edit it.
- `claude/skills/context-fold/references/context.md` carries the entry-shape rules
- Its `## What a working entry looks like` section is the criterion, asking what the domain owns, what each folder does now, and which trap a session would hit

## Decisions

### Three tiers of context

`CLAUDE.md` and `canon/REQUIREMENTS.md` load eagerly, `.claude/rules/` load on glob match, and `canon/context/` is read on demand through its catalog. One large `CLAUDE.md` would grow without bound. Nested `CLAUDE.md` files load cheaply but announce nothing, so a session never learns they exist.

Revisit when Claude Code tells a session which nested memory files exist before it opens them.

### Which tier a fact belongs in

A fact goes to `.claude/rules/` when it fires on a path being edited and violating it ships silently. Otherwise it goes to a context entry or a skill body. A `## Gotchas` line reaches too little. Eager loading does not substitute, since a session-start rule competes with the whole file and a glob-matched one arrives attached to the action.

The test rejects most of what it is run over, because a rule per gotcha rebuilds the `CLAUDE.md` the tiers exist to prevent. Firing is one axis of three.

- Conditional presence is the second, which a rule buys and a line in `CLAUDE.md` or a seed cannot, since an eager line loads into every session
- Updatability is the third, since governance sync carries a later fix to every installed project where a seed line stays fixed at its scaffold
- That makes the six rules `base` installs with no `paths:` glob correct as rules, five under `canon/` and one under `claude/`. Measured at `b6835a56` on 2026-09-26.
- The test ships as no rule, so it reaches a session through this entry alone. A target holds it only where this folder exists, and the seed does not state it.

### What bounds the eager tier

`canon/REQUIREMENTS.md` states a word cap the Canonical records stage gates. `CLAUDE.md` states none, and trims hold it instead, each moving a bullet into the skill or entry that reads it.

Reach never bounds either file, since nearly every fact touches two domains. Bounding by reach is how an eager architecture record once grew to forty entries and about 15k tokens in every session, after a numeric ceiling was tried and dropped because nothing enforced it.

- That record is retired, and a decision lives in the pull request that made it rather than in any context entry
- A session reads such a decision on demand, through git
- The pointer each other domain keeps carries no check, since nothing compares an entry against the one it defers to

### What each root holds

The project root splits three ways. One ignore line covers `.canon/`, so a record folder added later needs no row here, no ignore entry, and no manifest edit.

| Root       | Holds                                |
| ---------- | ------------------------------------ |
| `.claude/` | what Claude Code reads by path       |
| `canon/`   | what the toolkit authors and commits |
| `.canon/`  | every gitignored session record      |

Two tests sort the roots in order. Whether a file is committed separates `.canon/` from the rest, and whether Claude Code reads it by path then separates `.claude/` from `canon/`. Both lines are mechanical, which is their value. Sorting by what a folder is for would need a judgment and an ignore line for every new folder.

Revisit when Claude Code reads its files from a root a project can configure.

### Surfaces under each root

Five surfaces under `.claude/` are Claude Code's own: `settings.json` (with a per-machine `settings.local.json`), `hooks/`, `skills/` for the internal skills, `rules/` glob-matched against the path being edited, and `worktrees/`, where `EnterWorktree` requires its target.

The toolkit's committed surfaces sit under `canon/`.

- `canon/context/` is read on demand through its catalog
- `canon/config/` holds `baseline.json`, `pr-labels.toml`, and the install stamp, since Claude Code loads none of them by path
- `canon/REQUIREMENTS.md` is eager, and `canon/DESIGN.md` is read by `canon design render` and the design skills

### Migrating a project onto the roots

`canon migrate records` moves the gitignored record folders under `.canon/`, a filesystem act no commit records, since every folder it moves is untracked. `RECORD_ROOTS` resolves the old root behind the new one, so a target on an older binary keeps reading either root, and `CREATION_ROOT` names the new root for anything created.

Shipping the resolver and the move together was declined, since it would strand a target whose CLI does not know the new root. `canon migrate surface-roots` relocates the committed surfaces with `git mv` and rewrites their citations. The cost is a tracked `canon/` one character from the ignored `.canon/`, which a skimming reader cannot tell apart.

- The bare `.canon/` ignore spelling keeps a carve-out out of reach. Written as `.canon/*`, `!.canon/x/` would stage `x/`, while an unnamed new record folder stays ignored either way.
- Nothing enforces the bare spelling, and keeping the old ignore entries until every recorded target reported migrated was declined for the single line

### How entries get populated

`context-fold` runs at ship time through `git-ship` or `auto-ship`. It reads the diff, maps changed files to the entries that reference them, and rewrites the affected sections. `docs-sync` does the same for the README and `docs/*.md`. Ship time beats plan time because a plan drifts, while an entry should reflect what was built.

- New entries are not created automatically, since auto-creation pads the catalog with low-signal entries refreshed every pull request
- Create one by hand following `claude/skills/context-fold/references/context.md`, and `context-fold` keeps it current after

The rule does not reach the tooling stacks, which ship `development.md` and `ci.md` as user-owned seeds under `tooling/base/seeds/canon/context/`, a decision `tooling/base/reference.md` owns. Check both seed sources before concluding an entry is absent from a scaffolded project.

### Two shapes the file mapping misses

Both come from a change that removes a capability, and the `context-fold` body holds the sweep that catches them.

- The half-rewritten entry is refreshed at the top and left alone below, where the current opening lends authority to the stale remainder
- A sentence a change inverted from a distance, since a claim comparing two surfaces stays true only while both hold and its file often sits outside the diff

Rewriting only what the diff touched stays the default, overridden only inside an entry the run already edited.

### The sweep prompt reads rationale as current

The local classifier's sweep prompt reads a reason naming why an alternative was left out, what an earlier approach got wrong, or what a measurement caught as KEEP, even in the past tense. REWRITE needs a superseded figure beside its replacement, "now" or "no longer" marking a change, branch or PR narration, or rounds of candidates.

### A context entry's H2 set is closed

An entry carries `Overview`, `Layout`, and `Gotchas` as H2 and nothing else, and `canon context audit --gate` fails any other H2. Layout gives each working folder an H3 titled with its path, and Gotchas holds at most five one-line traps.

An entry carries no decisions. Context grew by about 160 words a merged pull request while the standard called decisions the reason the folder exists, and the pull request already records each one. Measured at `1d277111d` on 2026-10-17.

- `Decisions` is a retired section, reported everywhere and gated only under a prefix `src/context/shape-gated.ts` lists, so an unrebuilt entry never fails a push
- A `Sources` section for entries that are not about code was rejected
- Such an entry omits `Layout`, which the standard sanctions, and a project needing more overrides with its own rule, as compass does through `.claude/rules/project/context.md`
- The set ships to targets advisory, since no target runs `--gate`

## Gotchas

### A folder split is a ceiling rather than a fix

A split child re-accumulates content past the checkpoint the same way the flat entry did, and `claude/skills/context-fold/references/context.md` names no split as a length remedy on its own. Past 150 lines it asks three questions.

- Does the entry still cover a single domain
- Has it filled with content a command reproduces
- Does it carry its own history

Split only when the single-domain check fails, since a task filed as a split on line count alone has skipped the diagnosis. Measured 2026-08-05 with `canon context audit`, 22 of 48 audited entries sat past the checkpoint, and 14 of those were already sub-files of folders that had split.

### A weight remedy grows the file

Both remedies for a weight finding make the file longer. Collapsing heavy bullets into prose costs a break wherever the prose crosses the paragraph checkpoint, and a subheading breaking a long run costs about three lines. Report the post-remedy length as the number a folder decision is made against.

Projecting a split child's size from the source entry's section weights undercounts it, since the flat `## Decisions` and `## Gotchas` blocks distribute into children by topic. Distribute first, measure with `canon context audit`, and fix the file shape after.

### What a split strands

A reader enumerating a flat surface pins depth somewhere, so converting an entry to a folder can drop it from that reader's output rather than erroring. `walkEntries` pins it through `new Bun.Glob('*.md')` in `src/docs/read.ts`, and both `listTopics` and the `docs list` catalog read that one walk.

`bun run check` passes regardless, since every stage tests the files that exist rather than the names a command can reach. `internal/rules/claude/authoring-layout.md` carries the depth rule for four installable roots, and `canon/context/` and `docs/` sit outside it, so count the roots inside each reader before splitting either.

- A sub-area file resolves by its bare name once every root has been tried for a sibling file and for a folder
- The first root whose folders carry that name answers, and only where a single folder in that root carries it

### References a split strands

A split strands three classes of reference no gate reads.

- An entry's own direction words dangle, since the citation gate resolves backticked paths and a bare `above` names none
- A finding pinned to `<entry>:<line>` stops resolving while its task still ships
- Every root-relative link leaving the moved file deepens by one segment, and `canon context audit` reports nothing about the depth a path was written at

Grep for `above`, `below`, and the entry's own heading names before splitting, count the links leaving the file, and re-resolve every open line-pinned finding after.

### What earns a line in an always-loaded file

A document is always-loaded only when an `@` line in `CLAUDE.md` names it. Nothing gates the toolkit's own `CLAUDE.md` against the seed it distributes, `tooling/claude/seeds/CLAUDE.md`, so grep `^@` in `CLAUDE.md` and diff the anchor block against the seed before calling a document always-loaded.

An `@` line carries a catalog or a short document every session needs, such as a folder `index.md`. A lookup file such as `canon/DESIGN.md` stays a one-line key path.

- A line stays in either `CLAUDE.md` only when no core rule, path-scoped rule, eager import, or catalog already carries it
- A path-scoped rule fires on edit rather than during planning, so a design principle a command is planned against stays in the root even where a rule on `src/` restates it
- The seed keeps a line a core rule duplicates when a target installing it without governance would lose the instruction, which is why it keeps its Context bullet
- The root file keeps its own folder map, since the cap on re-derivable structure governs a second copy inside a per-domain entry, where the reader has already arrived
- The root map orients a reader who has opened no entry yet
